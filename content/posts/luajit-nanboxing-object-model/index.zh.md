每个 Lua 值——`nil`、`true`、`3.14`、`"hello"`、`{}`、`function() end`——都恰好占 8 字节。不是 16。不是 24。8 字节。和一个 `double` 一样大。

这个技巧叫做 **NaN-boxing**：一种利用 IEEE 754 浮点数 NaN 值中未使用的位模式，把类型信息直接编码进值表示的位打包技术。它是 LuaJIT 对象模型的基石，也是 LuaJIT 能在单个机器字中零开销地表示任何值的原因。

在本文中，你将完整学习 NaN-boxing 如何工作——从 IEEE 754 位布局到 TValue 联合体、GC64 与非 GC64 两种模式、GC 对象层次、双数模式，以及让垃圾回收器保持正确的写屏障。

> **核心要点**
> - NaN-boxing 利用 IEEE 754 中 2^52 个未使用的 NaN 位模式，把类型标签编码在 double 的高位。
> - 单个 `TValue` 联合体（8 字节）容纳任何 Lua 值：数字、布尔、nil、字符串指针、表指针等。
> - 非 GC64 模式：32 位类型标签 + 32 位值/指针。GC64 模式：13 位 NaN 标记 + 4 位标签 + 47 位指针。
> - 双数模式内联存储整数，只在必要时才回退到堆分配的双精度。
> - 写屏障不变量（黑色对象永不变白）让增量 GC 无需暂停世界。

## IEEE 754 NaN 空间——一个隐藏的游乐场

要理解 NaN-boxing，首先得理解 IEEE 754 双精度浮点格式。

### 位布局

64 位 double 分为三个字段：

```
 ┌──────────┬───────────────────┬────────────────────────────────────────┐
 │  符号(1)  │   指数(11)        │           尾数(52)                     │
 │    63    │     62-52         │            51-0                        │
 └──────────┴───────────────────┴────────────────────────────────────────┘
```

- **符号位**（bit 63）：0 = 正，1 = 负
- **指数**（bits 62-52）：偏移 1023；范围 0-2047
- **尾数**（bits 51-0）：小数部分（52 位精度）

值为：`(-1)^符号 × 2^(指数-1023) × 1.尾数`

### 什么是 NaN

一个值是 **NaN（非数）** 当：
- 指数域全为 1（0x7FF = 2047）
- 尾数非零

NaN 有两种：
- **安静 NaN（qNaN）**：尾数最高位（bit 51）置位 → 静默传播
- **信号 NaN（sNaN）**：bit 51 清零 → 使用时触发异常

### 关键洞察

指数域有 2048 个可能值（0-2047）。其中两个是特殊的：
- 0x000（全零）→ 零/非规格化数
- 0x7FF（全一）→ 无穷/NaN

当指数是 0x7FF 且尾数非零时，你得到一个 NaN。52 位尾数意味着 **2^52 - 1 个可能的 NaN 值**（减去尾数 = 0 的无穷情况）。

FPU 只生成**一个特定的 NaN 模式**：`0xFFF8000000000000`（「规范安静 NaN」）。所有其他 2^52 - 2 个 NaN 位模式**永远不会被浮点运算产生**。

LuaJIT 的洞察：这些未使用的 NaN 位模式是隐藏类型标签的完美场所。FPU 永远不会产生它们，所以任何具有 NaN 位模式的值都保证是 LuaJIT 类型标签，而非真实数字。

## TValue 联合体——8 字节统治一切

LuaJIT 对象模型的核心是 `TValue` —— 一个能用恰好 8 字节表示任何 Lua 值的联合体。

### 定义

```c
typedef LJ_ALIGN(8) union TValue {
  uint64_t u64;       /* 64 位模式与数字重叠 */
  lua_Number n;       /* 数字对象与分离的标签/值对象重叠 */
#if LJ_GC64
  GCRef gcr;          /* 带标签的 GCobj 引用 */
  int64_t it64;
  struct { int32_t i; uint32_t it; };  /* 整数值 + 内部标签 */
#else
  struct { union { GCRef gcr; int32_t i; }; uint32_t it; };
#endif
  struct { uint32_t lo; uint32_t hi; } u32;
} TValue;
```

同样的 8 字节可以解释为：
- 完整的 64 位 double（`n` 或 `u64`）
- 32 位类型标签 + 32 位值/指针（非 GC64）
- 47 位指针 + 4 位标签 + 13 位 NaN 标记（GC64）
- 两个 32 位半字（`u32.lo`、`u32.hi`）

### 类型检查

检查值的类型，LuaJIT 提取标签位：

```c
// 非 GC64：标签是顶部 32 位
#define itype(o)	((o)->it)
// GC64：标签是 bits 47-51
#if LJ_GC64
#define itype(o)	((uint32_t)(o)->it64 >> 47)
#endif
```

### 值提取

```c
// 提取 GC 指针
#define gcval(o)	((o)->gcr)
// 提取整数
#define intval(o)	((int32_t)(o)->i)
// 提取 double
#define numV(o)		((o)->n)
```

美妙之处：类型检查是单次位移位和掩码。无需间接寻址，无需虚函数表查找，无需单独的类型字段。只需对值本身做算术运算。

## 非 GC64 模式——32 位标签，32 位指针

在原始（非 GC64）模式下，TValue 布局很直接：

```
 ┌──────────────────────┬──────────────────────┐
 │   类型标签（32 位）    │   值（32 位）        │
 │      bits 63-32      │      bits 31-0       │
 └──────────────────────┴──────────────────────┘
```

### 内部类型标签

类型标签定义为负数（与 NaN 区域重叠）：

```c
#define LJ_TNIL      (~0u)   /* 0xFFFFFFFF = -1 */
#define LJ_TFALSE    (~1u)   /* 0xFFFFFFFE = -2 */
#define LJ_TTRUE     (~2u)   /* 0xFFFFFFFD = -3 */
#define LJ_TLIGHTUD  (~3u)   /* 0xFFFFFFFC = -4 */
#define LJ_TSTR      (~4u)   /* 0xFFFFFFFB = -5 */
#define LJ_TUPVAL    (~5u)   /* 0xFFFFFFFA = -6 */
#define LJ_TTHREAD   (~6u)   /* 0xFFFFFFF9 = -7 */
#define LJ_TPROTO    (~7u)   /* 0xFFFFFFF8 = -8 */
#define LJ_TFUNC     (~8u)   /* 0xFFFFFFF7 = -9 */
#define LJ_TTRACE    (~9u)   /* 0xFFFFFFF6 = -10 */
#define LJ_TCDATA    (~10u)  /* 0xFFFFFFF5 = -11 */
#define LJ_TTAB      (~11u)  /* 0xFFFFFFF4 = -12 */
#define LJ_TUDATA    (~12u)  /* 0xFFFFFFF3 = -13 */
#define LJ_TNUMX     (~13u)  /* 0xFFFFFFF2 = -14 */
```

每个标签比前一个小 1，从 -1（0xFFFFFFFF）开始。解释为 double 时，这些都落在 NaN 区域（指数 = 0x7FF，尾数非零）。

### 每种类型如何装入

```
 NIL/TRUE/FALSE:          整数:                    GC 指针:
 ┌──────────┬──────────┐  ┌──────────┬──────────┐  ┌──────────┬──────────┐
 │ LJ_TNIL  │  (零)    │  │ LJ_TNUMX │   42     │  │ LJ_TSTR  │  ptr     │
 │ 0xFFFF.. │  0x0000  │  │ 0xFFFE.. │  0x002A  │  │ 0xFFFB.. │  0x1A2B  │
 └──────────┴──────────┘  └──────────┴──────────┘  └──────────┴──────────┘
  标签即值，无需载荷        标签 + 32 位整数          标签 + 32 位指针

 双精度（堆分配）：
 ┌──────────────────────────────────────────────────┐
 │  完整 64 位 double 值（标签 = LJ_TNUMX）          │
 │  「指针」指向堆分配的 double                      │
 └──────────────────────────────────────────────────┘
```

- **nil、false、true**：标签就是值。无需载荷。`nil` = LJ_TNIL 标签 + 零载荷。
- **整数**（双数模式）：标签 = LJ_TNUMX，低 32 位 = 有符号整数值。
- **GC 指针**（字符串、表、函数）：标签 = 类型特定，低 32 位 = 指向 GC 对象的指针。
- **双精度**（无法内联时）：标签 = LJ_TNUMX，低 32 位 = 指向堆分配 `lua_Number` 的指针。

### 局限

非 GC64 模式用 32 位指针，限制地址空间为 4GB。对多数 Lua 应用够用，但对大内存占用的服务器或游戏是约束。这就是 GC64 模式存在的原因。

## GC64 模式——8 字节中的 64 位指针

现代 64 位系统能寻址远超 4GB。GC64 模式扩展 LuaJIT 使用完整 64 位指针——仍然只用 8 字节。

### 布局

```
 ┌────────────┬──────────┬────────────────────────────────────────────┐
 │ NaN(13位)  │标签(4位)  │         指针（47 位）                        │
 │ bits 63-52 │bits 51-48 │            bits 47-0                       │
 └────────────┴──────────┴────────────────────────────────────────────┘
```

- **顶部 13 位**：全 1（0x1FFF）—— NaN 标记
- **接下来 4 位**：类型标签（最多支持 16 种类型）
- **底部 47 位**：实际指针（128TB 可寻址）

### 为什么是 47 位？

x86-64 处理器使用 48 位虚拟地址（符号扩展到 64 位）。用户空间地址限制在 48 位，LuaJIT 用其中 47 位——提供 128TB 可寻址空间。对任何 Lua 程序都绰绰有余。

### GC64 中的类型检查

```c
#if LJ_GC64
#define itype(o)  ((uint32_t)(o)->it64 >> 47)
#endif
```

标签通过右移 47 位提取。顶部 13 位全为 1 确认这是 NaN-boxed 值（不是真实 double）。

### 权衡

GC64 模式需要更复杂的类型检查（右移 47 位 vs 提取顶部 32 位）和指针掩码。开销最小（每次类型检查多 1-2 条指令），但在紧循环中可测量。收益——128TB 地址空间 vs 4GB——对现代应用至关重要。

## GC 对象层次——一切都是 GCobj

LuaJIT 中每个垃圾回收对象共享一个公共头：

```c
#define GCHeader  GCRef nextgc; uint8_t marked; uint8_t gct
```

- `nextgc`：指向 GC 链中下一个对象的指针
- `marked`：三色 GC 的颜色位（白/灰/黑 + 标志）
- `gct`：GC 类型（区分字符串、表、函数）

### GCobj 联合体

```c
typedef union GCobj {
  GChead gch;     /* 公共头 */
  GCstr str;      /* 字符串 */
  GCupval uv;     /* 上值 */
  lua_State th;   /* 线程 */
  GCproto pt;     /* 原型 */
  GCfunc fn;      /* 函数（闭包） */
  GCcdata cd;     /* C 数据（FFI） */
  GCtab tab;      /* 表 */
  GCudata ud;     /* 用户数据 */
} GCobj;
```

```
                        ┌─────────┐
                        │GCHeader │
                        │nextgc   │
                        │marked   │
                        │gct      │
                        └────┬────┘
              ┌──────────────┼──────────────┐
              │              │              │
        ┌─────┴─────┐  ┌────┴────┐  ┌─────┴─────┐
        │  GCstr    │  │  GCtab  │  │  GCfunc   │
        │           │  │         │  │           │
        │ hash      │  │ array   │  │ ffid      │
        │ len       │  │ hash    │  │ pc        │
        │ data[]    │  │ metatable│  │ upvalues  │
        └───────────┘  └─────────┘  └───────────┘
```

### 关键 GC 对象类型

**GCstr（字符串）**：头 + 哈希算法 + 字符串 ID + 哈希 + 长度 + 数据。字符串被驻留——相同字符串共享同一对象。

**GCtab（表）**：头 + 数组部分（快速整数键）+ 哈希部分（其他键）+ 元表。表是 Lua 中唯一的数据结构——用于数组、对象、字典和模块。

**GCfunc（函数）**：头 + 函数 ID（ffid）+ 上值指针。区分 C 函数（ffid > 0）和 Lua 函数（ffid = 0）。

**GCproto（原型）**：头 + 字节码 + 常量 + 上值信息 + 调试信息。Lua 函数的编译表示。

**GCcdata（C 数据）**：头 + C 类型 ID + 数据。FFI 用于表示 C 类型。

**GCudata（用户数据）**：头 + 用户数据类型 + 环境 + 长度 + 数据。带可选元表的原始内存块。

**GCupval（上值）**：头 + 关闭标志 + 值指针。表示来自外层作用域的变量。

### `gct` 字段

头中的 `gct` 字段在 GC 遍历期间区分对象类型：

```c
#define LJ_TSTR    (~4u)
#define LJ_TUPVAL  (~5u)
#define LJ_TTHREAD (~6u)
#define LJ_TPROTO  (~7u)
#define LJ_TFUNC   (~8u)
#define LJ_TTRACE  (~9u)
#define LJ_TCDATA  (~10u)
#define LJ_TTAB    (~11u)
#define LJ_TUDATA  (~12u)
```

当 GC 遍历对象时，根据 `gct` 切换到对应的遍历函数（标记对象的子对象）。

## 双数模式——无需分配的整数

Lua 5.1 规范规定所有数字都是 double。但为每个整数都分配堆对象太浪费了。LuaJIT 的**双数模式**（LJ_DUALNUM）解决了这个问题。

### 问题

```lua
local x = 0
for i = 1, 1000000 do
  x = x + 1    -- 如果每个整数都堆分配，这会创建 100 万个对象！
end
```

没有双数模式，每次整数运算都会分配堆对象、触发 GC 压力、变慢。

### 解决方案

双数模式尽可能把整数**内联**存储在 TValue 中：

```
 整数（内联）：            双精度（堆分配）：
 ┌──────────┬──────────┐  ┌──────────┬──────────┐
 │ LJ_TNUMX │   42     │  │ LJ_TNUMX │  ptr     │
 │ 0xFFFE.. │  0x002A  │  │ 0xFFFE.. │  0x1A2B  │
 └──────────┴──────────┘  └──────────┴──────────┘
  标签 + 32 位整数           标签 + 指向堆 double 的指针
```

- **内联整数**：标签 = LJ_TNUMX，低 32 位 = 有符号整数值。无堆分配。
- **堆 double**：标签 = LJ_TNUMX，低 32 位 = 指向堆分配 `lua_Number` 的指针。

### 类型检查

```c
// 这个值是内联整数吗？
#define tvisint(o)	(itype(o) == LJ_TNUMX && (int32_t)(o)->i != 0)
// 这个值是堆 double 吗？
#define tvisnum(o)	(itype(o) == LJ_TNUMX && !tvisint(o))
```

等等——两者标签都是 LJ_TNUMX。怎么区分？技巧在于：整数用高位存标签、低位存整数；堆 double 的指针解释为两个 32 位半字时，有不同的位模式。实际检查更微妙——它依赖指针值（很大）与小整数有不同的位模式这一事实。

### 性能影响

有了双数模式：
- 整数运算：无堆分配，无 GC 压力，单条指令
- 混合整数/浮点：需要时自动提升为 double
- 溢出：当整数超过 32 位范围时，提升为堆 double

这对性能至关重要：多数循环使用整数，避免分配是巨大的收益。

## 写屏障——保持 GC 正确

LuaJIT 使用**增量三色标记-清除 GC**。三色抽象：

- **白色**：尚未到达（回收候选）
- **灰色**：已到达但未扫描（子对象未标记）
- **黑色**：已到达且已扫描（子对象已标记）

### 不变量

**黑色对象永远不指向白色对象。**

这是增量 GC 的根本不变量。如果它成立，GC 可以安全回收白色对象——它们不可达。

### 不变量为何会被破坏

在传播阶段，GC 正在把灰色对象变黑。同时，修改器（运行的 Lua 代码）在修改对象。考虑：

1. 对象 A 是黑色（已扫描）
2. Lua 代码执行：`A.field = B`，其中 B 是白色
3. 现在 A（黑色）指向 B（白色）——不变量被破坏！
4. GC 可能完成标记而永远不到达 B → B 被错误回收

### 写屏障

**写屏障**检测并修复不变量违反。当黑色对象获得对白色对象的新引用时：

**前向屏障**（`lj_gc_barrierf`）：对非表对象——要么标记白色对象（把边界前移），要么把黑色对象重新灰色。

**后向屏障**（`lj_gc_barrierback`）：对表——把对象移回灰色（grayagain 列表）。更便宜，因为表频繁被修改。

```
 修改器写入：A.field = B     (A 是黑色，B 是白色)

 ┌──────────┐                ┌──────────┐
 │  A       │                │  B       │
 │ (黑色)   │───field──────▶│ (白色)   │
 └──────────┘                └──────────┘
       │
       │ 写屏障触发：
       │ 选项 1：标记 B（使其变灰）
       │ 选项 2：把 A 重新灰色（移回 grayagain）
       ▼
 ┌──────────┐                ┌──────────┐
 │  A       │                │  B       │
 │ (黑色)   │───field──────▶│ (灰色)   │  ← 不变量恢复
 └──────────┘                └──────────┘
```

### 为什么表用后向屏障？

表是 Lua 中被修改最频繁的对象。用前向屏障需要在每次表赋值时标记被存储的值——做百万次表写入时很贵。后向屏障更便宜：只需把表重新灰色，GC 稍后会重新扫描它。

### 上值屏障

当上值被关闭（其变量离开作用域）时，GC 必须确保关闭的值不指向已回收对象。上值屏障（`lj_gc_barrieruv`）专门处理这种情况。

## 为什么 NaN-boxing 重要——性能影响

NaN-boxing 不仅是巧妙——它有真实的性能后果。

### 零空间开销

每个 Lua 值恰好 8 字节。一个 x86-64 缓存行（64 字节）容纳 **8 个值**。对比：

```
 LuaJIT（NaN-boxing）：     V8（标记指针）：        CPython（PyObject）：
 ┌──────────────────┐     ┌──────────────────┐     ┌──────────────────┐
 │ 8 字节/值         │     │ 8 字节/值         │     │ 16 字节头         │
 │ 无额外头          │     │ + 隐藏类          │     │ + 8 字节指针      │
 │ 类型在位中        │     │ 类型在指针中      │     │ 类型在头中        │
 └──────────────────┘     └──────────────────┘     └──────────────────┘
 ~8 字节有效             ~8-16 字节有效           ~24+ 字节有效
```

### 快速类型检查

类型检查是位掩码和比较——单条指令。无虚函数表查找，无间接寻址：

```c
// LuaJIT：类型检查是一条指令
if (itype(o) == LJ_TTAB) { ... }

// CPython：类型检查是指针解引用
if (Py_TYPE(o) == &PyList_Type) { ... }
```

### 整数运算无分配

双数模式意味着整数循环不分配。对比：

```lua
-- LuaJIT：整数无分配
local x = 0
for i = 1, 1000000 do x = x + 1 end  -- 零分配

-- 没有双数模式：1,000,000 次堆分配
```

### 缓存效率

紧凑的值意味着更多值能放入缓存。含 1000 个数组元素的表在 LuaJIT 中占 ~8KB（能放入 L2 缓存），CPython 中 ~16-24KB（可能放不下）。

### 权衡

NaN-boxing 需要更复杂的类型检查（位操作）并限制指针空间（GC64 47 位，非 GC64 32 位）。但对值小且多的脚本语言，空间节省占主导。

## 常见问题解答

### 为什么专门用 NaN？

NaN 位模式保证永远不会被 FPU 产生。任何具有 NaN 位模式的值都保证是 LuaJIT 类型标签，而非真实数字。这让类型检查安全——你永远不会把真实 double 和类型标签搞混。

### 如果真的计算出了 NaN 会怎样？

LuaJIT 的规范 NaN 是 `0xFFF8000000000000`。如果 FPU 计算出 NaN（如 `0/0`），它产生这个特定模式，LuaJIT 识别为「非数」（LJ_TNUMX 标签 + NaN 载荷）。所有其他 NaN 位模式都是类型标签。

### NaN-boxing 是 LuaJIT 独有的？

不是。JavaScriptCore（WebKit 的 JavaScript 引擎）也用 NaN-boxing。LuaJIT 把它推广到动态语言，但技术早于它。关键洞察——用未使用的 IEEE 754 位模式做类型标签——适用于任何语言实现。

### GC64 如何影响性能？

GC64 模式需要稍复杂的类型检查（右移 47 位 vs 提取顶部 32 位）和指针掩码。开销最小（每次类型检查多 1-2 条指令），但在紧循环中可测量。收益——128TB 地址空间 vs 4GB——对现代应用至关重要。

### 我能禁用双数模式吗

可以。编译不带 `LJ_DUALNUM` 的 LuaJIT——所有数字都变成堆分配的 double。这简化了实现（无需整数/双精度区分），但对整数密集型代码性能影响显著。
