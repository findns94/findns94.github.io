# 447 座神山变成地铁图：《山海经》知识图谱是怎么建成的

《山海经》记下了 447 座具名山岳，分属 26 条山系，篇末总结句逐条相加声称总里程 97,358 里——约合四万公里，差不多是地球赤道周长。但全书没有告诉你任何一座山究竟在哪里：没有坐标，没有纪年，传世文本里也没有图。它给你的只是纯粹的拓扑关系：「又东三百里，曰某某之山」。这恰好就是一张地铁图承载的信息，也恰好是知识图谱能装下的信息。

本文是「机器阅读《山海经》」系列 6 篇中的第 3 篇。[系列总览](/posts/machine-reading-shanhaijin-knowledge-graph/) 讲这个项目是什么、为什么要做；本篇做工程层的深潜：标注体系怎么设计、抽取管线怎么运转、知识图谱里究竟有什么，以及大多数技术文章会略过的部分——**哪些声明的 schema 至今还是空的**。

<!-- more -->

> **核心要点**
> - 《山海经》知识图谱含 **2,141 个实体(15 个类型已填充)** 与 **7,113 条关系**——5,896 条空间关系加 1,217 条生物关系（项目数据，2026）。
> - 关系由**规则正则从标注语料中抽取，而非 LLM 推断**：空间关系 88.3%、生物关系 89.2% 落在自动高置信档，LLM 推断产出为零。
> - 标注层用**三套互斥符号族**——实体 `〖…〗`、熟语 `〘…〙`、行为 `⟦…⟧`——使标记语法永不与 Markdown 冲突。
> - 1,041 条记载单元按 **7 类句式(P1–P7)** 解析，是散文到图边的桥梁：一条山条目等于一条记载。
> - 构建脚本把 **12 个 JSON 源** 合并成 6 个按组件拆分的文件，背后是 **29 条硬断言**，运行时零依赖，源语料缺席时优雅跳过。

## 《山海经》知识图谱里究竟有什么？

有 2,141 个规范实体、5,896 条空间关系与 1,217 条生物关系，来自 18 篇、约 32,316 字的文言原文。整个图谱是静态 JSON——没有数据库、没有服务端、没有查询引擎。已填充的实体类型共 15 类，最大的是山岳（576）、水道（405）、物产矿物（399）与异兽（272）。

两族关系刻意不对称：空间关系描述事物之间的相对位置，生物关系描述什么东西住在哪里、吃了会怎样。

有两个数字需要说明。第一，`in_chain` 高达 4,824 条不是 bug——它是「同属一条山系」的无向两两闭包：9 站的山系贡献 36 对，40 站的山系贡献 780 对。它表达的是「这些山属于同一条路线」。第二，`located_at` 只有 8 条，因为《山海经》极少给绝对位置，几乎永远给相对位置。

> **引用胶囊：** 《山海经》知识图谱含 2,141 个实体（15 个类型已填充）与 7,113 条关系——5,896 条空间关系（`in_chain` 4,824、`adjacent_to` 438、`distance_from` 405、`water_connect` 221、`located_at` 8）加 1,217 条生物关系（`produces` 803、`inhabits` 271、`has_efficacy` 90 及四个更小的类型）。来源：项目构建产物，2026 年 10 月。

## 怎么给一部两千多年前的文本加标注，又不破坏它？

加一层原文不可能自带的括号，并让三族括号彼此互斥。标注层不修改、不重排、不规范化任何一个原文字符，只把区间包起来。去掉全部标记后，纯文本必须与底本逐字一致，而这一条由 lint 在每一篇上强制执行。

三族括号刻意取自 Markdown 与中文标点都不使用的 Unicode 区段：

| 层 | 括号 | 码位 | 标记对象 | 示例 |
|---|---|---|---|---|
| 实体层 | `〖 … 〗` | U+3016 / U+3017 | 世界中的对象 | `〖=招搖之山〗` |
| 熟语层 | `〘 … 〙` | U+3018 / U+3019 | 语言自身的固化单元 | `〘※…〙` |
| 行为层 | `⟦ … ⟧` | U+27E6 / U+27E7 | 动作与关系 | `⟦○名曰⟧` |

实体括号内放一个类型符号。声明了 20 个名词类，另有 2 个动词类放在行为括号里：

```
=  山岳      ~  水道      +  异兽      *  草木
?  神祇      ◆  方国      •  物产      ^  祠礼
:  祭祀场所  !  方位      $  里程      [  灾异
@  人物      #  身份      %  时间      _  概念
{  典籍      &  族群      <  鸟兽      >  方位段
◈  行为动词  ○  关系动词
```

选 `〖〗`（U+3016/3017，白色六角括号）与 `⟦⟧`（U+27E6/27E7，数学白方括号）不是为了好看。20 个类型符号里有 10 个——`#`、`_`、`[`、`$`、`:`、`{`、`~`、`<`、`>`、`&`——同时也是 Markdown 语法。把它们包进一对 Markdown 解析器不认识的括号，它们就失效了：`〖#身份〗` 打不开标题，`〖_概念〗` 打不开斜体。符号在括号内保持可读，在渲染器外保持无害。

<!-- [UNIQUE INSIGHT] 标注规范声明了 20 个名词类，但实际产出的索引只填充了 15 个。空置的 5 类——祭祀场所 `:`、时间 `%`、典籍 `{`、族群 `&`、方位段 `>`——在本语料中没有任何可辩护的实例，行为动词 `◈` 同样为空。标注器被配置成「跳过而非猜测」，所以空类意味着「文本里没有我们敢标的实例」，而不是「工具坏了」。这是一个刻意的设计结果：管线宁要一个小而可验证的 schema，也不要一个名义上完整却塞满噪声的 schema。 -->

消歧有两条路径。内联形式是 `〖TYPE 显示名|规范名〗`，竖线前是渲染文本，竖线后进索引与 tooltip：

```
〖=招搖之山|南山經-招搖之山〗
```

另一条是外挂 JSON 映射表，而在本项目里真正被使用的是后者：241 条记录以名称为键，每条列出该名称重出的卷次。歧义最重的是「三百里」，横跨 13 篇；其后有 150 个名称恰好重出两篇。

<!-- [ORIGINAL DATA] 对 18 篇标注文件的普查统计出 4,104 处实体标记与 108 处行为标记。熟语族 `〘〙` 出现 0 次，内联消歧语法 `〖TYPE 显示名|规范名〗` 同样出现 0 次——241 条消歧记录全部存放在外挂 JSON 映射表里。这两者都是「功能已建好、但本语料没有用上」的情况。 -->

## 规则标注器如何决定哪个区间胜出？

先把所有候选区间收集完，再按「长优先」解决重叠，最后才写入括号。标注器是一个 `SpanTagger` 类，从不就地改文本：每条规则只登记 `(start, end, symbol)` 三元组，渲染在最后一次性完成，中间经过一次确定性排序。

这个顺序比听起来重要得多。如果边匹配边插括号，后面所有偏移都会漂移，本该胜出的长匹配可能横跨一个已经插好的短标记。先收集再渲染让整趟扫描的索引保持稳定。裁决规则就是一行：

```python
ordered = sorted(self.spans, key=lambda s: (s[0], -(s[1] - s[0]), s[2]))
```

从左到右、长区间优先、同长按符号排序——第一个占住某区域的区间留下，与之重叠的候选全部丢弃。正是这一行保证了三层互斥：实体永远不可能嵌进行为层里，因为内层区间压根不会被写出。

规则本身是带守卫的正则，而不是裸模式。山名规则会匹配「两字 + 之山」，但守卫会在前一个字符是方位词或数词时拒绝该匹配——因为「又東三百里，曰堂庭之山」必须产出 `〖!東〗` `〖$三百里〗` `〖=堂庭之山〗` 三个独立区间，而不是一个吞掉方位与里程的大区间。

<!-- [PERSONAL EXPERIENCE] 整个项目里最难划的边界就是山名本身。文言山名常常只有一到两个字——柢山、基山、羽山——而两字的匹配窗口会顺手吞掉紧随其后的动词或介词。最后的做法是把山名主体限制在一到两字，并接受「三天子鄣山」这类长专名会被漏标。漏掉一座山是可以补救的；标错一座山会污染整条山系链，而所有空间关系都建立在链上。 -->

这套策略在文档里写作「宁缺勿错」，并且直接体现在验收标准里：与底本的实质差异 0 处、嵌套标注 0 处、边界错误 0 处。标注覆盖率落在 35.14%，听起来不高——但别忘了虚词、助词，以及「有兽焉，其状如……」这类程式化脚手架本身不携带实体信息。

## 管线一共九步，分别做什么？

九步，而且顺序是硬的，因为每一阶段都消费上一阶段的 ID。依赖链就是整个架构：段落编号错了，所有实体引用、每条关系的溯源字段、每个地图坐标都得重建。

| # | 阶段 | 产物 | 说明 |
|---|---|---|---|
| 01 | 校勘 | `chapter_md/*.tagged.md` | 句读、异体字、注文分层 |
| 02 | 结构 | 段落编号 `（NNN-PPP）`、26 条山系、18 篇 | 山系首句、逐山条目、篇末总结句 |
| 03 | 实体 | 2,141 个实体、别名、消歧表 | 声明 20 个名词类 + 2 个动词类 |
| 04 | 记载单元 | 1,041 条记载，7 类句式(P1–P7) | 替代史书类语料使用的「事件」模型 |
| 05 | 关系 | 5,896 条空间关系 + 1,217 条生物关系 | 纯规则抽取，只读第 03、04 阶段 |
| 06 | 本体 | 133 个已分类实体、5 个分类文件 | L1–L5 分类阶梯 |
| 07 | 推理 | 63 条已记录矛盾 | 逐条累计与篇末总结句交叉验算 |
| 08 | 知识库管驭 | 覆盖度指标、质量门禁 | 文本完整性、符号白名单、边界错误 |
| 09 | 应用构造 | 山海图、聚焦视图、实体浏览、检索 | 消费构建脚本产出的 JSON |

第 04 阶段是概念上的转折点。同类项目处理史书语料时建的是**事件**——战役、继位、诏令——每个事件带日期与人物表。《山海经》几乎没有这些。它有的是反复出现的描述模板，于是管线把「事件」换成「记载单元」：一句原文对应一条原子陈述。

## 为什么用规则抽取，而不是让大模型去推断？

因为文本是程式化的，而程式化文本用规则解析更便宜、也更可审计。图谱里每条关系都记录了它是怎么来的，而 7,113 条里有 7,105 条的答案是「对标注语料的确定性模式匹配」。LLM 推断的贡献是零。

溯源字段是显式的。每条关系带一个 `auto` 布尔值、一个 `evidence_type` 字符串（写明是哪条模式命中：`chain_step_exact`、`product_pattern`、`creature_pattern`、`efficacy_pattern`、`sacrifice_pattern`、`genealogy_pattern`、`water_flow`、`explicit_location`），以及一个置信度对象，内含分值、档位和产生该分值的信号清单。

档位不是装饰。一条空间关系在「链步方位完整 + 里程精确」时得 0.95；当所在篇的总结句与逐条里程之和相差超过 5% 时降到 0.85。这个降级是诚实的记账：单步本身仍然可信，但它所属的链存在文本问题，所以该关系被标为待复核，而不是悄悄升档。

> **引用胶囊：** 5,896 条空间关系中有 5,206 条(88.3%)进入自动高置信 A 档，690 条(11.7%)因所属山系的声明总里程与逐条累加不符而降为 B 档；1,217 条生物关系中有 1,086 条(89.2%)进入 A 档。两族关系中由 LLM 推断产出的数量均为零。来源：项目构建产物，2026 年 10 月。

那 11.7% 不是要被调参消掉的噪声，而是管线在检测「原文自相矛盾」——这正是[本系列第 2 篇](/posts/shanhaijing-63-contradictions-machine-reading/)的主题：63 条矛盾被逐条编目，并刻意不作修正。最极端的一条是某山系的声明总里程与逐条累计相差数千里的量级，远非四舍五入可以解释，[第 6 篇](/posts/shanhaijing-missing-character-429-percent/)专门审计了这一处。

## 1,041 条记载单元怎么变成 7,113 条关系？

靠 7 类句式。《山海经》不是自由散文，而是被重复了 447 次的模板，只换填空位。每个句式写一条正则，图谱基本就掉出来了。

| 句式 | 形状 | 条数 |
|---|---|---:|
| P1 物产 | `X山，其陽多A，其陰多B` | 448 |
| P4 水系 | `X水出焉，而南流注于Y` | 253 |
| P2 异兽 | `有獸焉，其狀如Y而Z，其名曰W` | 191 |
| P5 山系总结 | `凡X山之首，自Y至于Z，凡N山，M里` | 57 |
| P3 草木 | `有草焉，其狀如Y，其名曰W，食之不Z` | 41 |
| P7 征兆 | `見則其國大旱` | 31 |
| P6 神人 | `有人曰X，Y形` | 20 |

每个句式填一组固定字段。一条 P2 异兽记载携带异兽名、被拆成「原型 + 差异列表」的形态描述、姿态、叫声、花纹与行为；一条 P4 水系记载携带源头山、流向方位与汇入水体；一条 P7 征兆记载携带触发异兽与后果。

![一幅木刻插图，画的是一足异兽夔，右侧竖排中文说明文字，出自吴任臣 1667 年《山海经广注》](/posts/shanhaijing-knowledge-graph-pipeline/images/kui-creature-woodblock.jpg)

夔是教科书式的 P2 记载。原文给了它名字、原型（牛）、一组差异（苍身、无角、一足）、一个行为（出入水），又因为它同时是征兆，再给了一条关于风雨随之的 P7 记载。两类句式、两条记载单元、两族不同关系，原文只有一句话。

抽取规则由 15 条显式不变量守护，并由一个独立校验脚本复算。其中三条承担了大部分工作。「无 X」绝不生成关系——「無草木」不代表这座山不产出任何东西，只代表文本没有列举。`inhabits` 边永远指向「异兽 → 山」，而 `produces` 永远指向「山 → 物产」，两族因此不可能混淆。谱系边必须有显式「生」字，妻、孙不另建关系类型就不会被升格。

这份纪律也解释了为什么一只名兽不在图谱里。《山海经》确实写了九尾狐，但在它出没的那座山上，原文是**描述** 它而非**命名** 它——「其狀如狐而九尾」——于是没有具名异兽实体，也就没有 `inhabits` 边。[本系列第 5 篇](/posts/shanhaijing-nine-tailed-fox-missing/)讲的就是这个缺口，以及管线为什么选择让它留在明面上，而不是补一个推断出来的名字。

## 构建脚本内部：12 个源、6 个文件、29 条断言

它把 12 个只读 JSON 源合并成 6 个按组件拆分的文件，校验 29 条硬断言，任何不变量被打破就拒绝产出。脚本是 `scripts/build-shanhaijin-data.mjs`，挂在 `prebuild` 上运行。

12 个输入是：山系地图、26 个路线文件、异兽分布、物产产地、篇章原文、实体索引、分类树、别名表、空间关系、生物关系、消歧表、447 山坐标。产物是一个单体 `data.json` 加 6 个拆分文件——`panorama-data`、`panorama-layout`、`map-data`、`graph-data`、`entity-data`、`search-data`——再加一个轻量 `meta.json` 与一个扁平 `entity-names.json` 供客户端标注用。

拆分才是关键。`graph-data.json` 只带实体与两族关系，图谱页因此只加载 5.5 MB 的图数据，别的都不碰。`search-data.json` 只带实体、异兽、物产与山系，检索框永远不碰关系表。单体文件仍然保留以兼容旧代码，但站上每个页面加载的都是切片。

29 条断言才是真正的规格说明。其中 12 条是全局不变量——恰好 26 条山系、恰好 447 站、恰好 2,141 个实体、恰好 5 种空间关系、恰好 7 种生物关系、至少 200 条消歧记录、恰好 5 篇山坐标，以及若干针对具名记录的点检。另外 17 条是山系名抽取的回归表：

```js
const EXPECTED_SHANXI = {
  'ROUTE-001-1': '䧿山',        // 甲式
  'ROUTE-002-1': '華山',        // 乙式
  'ROUTE-003-2': '管涔之山',    // 甲式，中间夹插入语
  'ROUTE-005-1': '薄山',        // 乙式
  'ROUTE-001-2': '南次二經',    // 丙式：回退经名
  // …… 还有 12 条
}
```

这张表存在的原因是山系名有三种语法形态，没有一条正则能同时吃下。乙式把范围名放在「之首」之前；甲式放在「曰」之后；丙式根本没给，正确答案是回退成经名。三种顺序跑反了，会让一部分山系静默取到错名字——这种失败在聚合统计里完全看不见，只有把每一种逐条点名断言才能抓到。

两个工程细节值得抄。脚本运行时只 import `node:fs`、`node:path`、`node:url`，而它产出的 JSON 是提交进仓库的——这就是为什么在源语料不存在的环境里构建仍能通过：

```js
if (!existsSync(MAP_DATA)) {
  console.warn('[build-shanhaijin-data] source corpus absent; skipping rebuild')
  process.exit(0)
}
```

CI 检出的是博客仓库，不是研究语料库。输入缺失就硬失败，会让每一次改文章的部署都挂掉；优雅跳过并以已提交产物兜底，意味着数据层在能复现的地方复现、在不能复现的地方至少保持稳定。为准确起见补一句：脚本头部注释声称零依赖，但文件确实 import 了 `typescript`，用来在构建期转译两个纯布局模块。这是构建期依赖而非运行时依赖，但注释是过时的。

## 为什么叫它地铁图？

因为对于一部只编码拓扑、不给地理的文本，地铁图就是正确的可视化形式。26 条线、447 个站、97,358 里声称的里程——而源文本里没有任何坐标。

地铁图刻意丢掉真实地理，只保留顺序、相邻与换乘。这正是《山海经》提供的东西。每条山系是一条线，每座山是一个站，每个「东三百里」是带里程标签的站间区间。出现在多篇里的实体是换乘站——同一个名字被两条线服务——消歧表里这样的名字有 241 个。

> **引用胶囊：** 《山海经》记载了 26 条山系、447 座山，声称总里程 97,358 里，却不提供任何坐标、年代与绝对位置。因此知识图谱编码的是拓扑——山系归属、相邻、里程、方位——而不是地理，这也是可视化选择地铁图而非中国地图的原因。来源：项目结构产物，2026 年。

图谱对这个区别是诚实的。坐标靠沿链累加里程推算，因此每个坐标都标为「估算」而非「实测」；实体层被切成三个置信层，而不是当成一份同质数据集端上来。九尾狐的缺口与 63 条已记录矛盾出于同一原则：图谱报告文本说了什么，也包括文本沉默或自相矛盾的地方。

## 常见问题

### 《山海经》知识图谱里有多少实体和关系？

2,141 个规范实体、15 个已填充类型、5,896 条空间关系、1,217 条生物关系，另有 2,117 条别名记录与 241 条消歧记录。整个图谱以静态 JSON 输出，背后没有数据库或查询引擎（项目构建产物，2026）。

### 这些关系是大模型抽出来的吗？

不是。每条关系都由确定性正则模式从标注语料中产出。7,113 条里有 7,105 条带 `auto: true` 与具名 `evidence_type`，LLM 推断为零，8 条由人工撰写——3 条有争议的同一性判断加 5 条手工别名（项目构建产物，2026）。

### 标注规范声明了 20 类，为什么只有 15 类有数据？

因为祭祀场所、时间、典籍、族群、方位段这 5 类在本语料中没有任何可辩护的实例，行为动词类同样为空，而标注器被配置成「跳过而非猜测」。声明了却为空的类，是一个设计结果而不是缺陷（项目标注普查，2026）。

### 什么是记载单元？为什么不沿用「事件」？

记载单元是一句话里的一条原子陈述——一份物产清单、一段异兽描述、一条水系、一句山系总结。史书类语料用带日期与人物的事件建模，但《山海经》没有可靠纪年，于是管线改为抽取 1,041 条记载单元，归入 7 类句式（项目记载索引，2026）。

### 逐条累加与总结句不符时，为什么总里程还是 97,358 里？

因为原文的篇末总结句与逐条里程本来就不一致，而管线选择记录这个不一致而不是抹平它。26 条山系里只有 2 条完全对得上，17 条里程有差，6 条里程与山数都有差。这 63 条矛盾是本系列第 2 篇的主题。

## 结论

这个项目的工程主张很窄，也可以被检验：一部 32,316 字的文言文本，可以变成一张 2,141 个实体、7,113 条关系的知识图谱，而**抽取阶段零 LLM 推断**——靠的是一层不会破坏 Markdown 的括号标注、一个保证互斥的长优先区间标注器、7 类吸收了文本自身程式化结构的句式，以及一个在任何不变量失守时拒绝产出数据的构建脚本（内含 29 条断言）。

最重要的部分恰恰是缺失的部分。5 个声明的实体类是空的；熟语族定义了却从未使用；内联消歧语法存在，而语料实际走的是外挂映射表；书里最著名的异兽之一没有关系，因为原文从未为它命名。每一个缺口都是一个「宁可不猜」的决定，而每一个都被写进数据里，而不是塞进脚注。
