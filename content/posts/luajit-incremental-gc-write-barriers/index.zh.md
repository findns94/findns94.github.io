LuaJIT 的垃圾回收器与你的代码并发运行。它从不久停世界超过几微秒。秘密是一个简单的不变量：**黑色对象永远不指向白色对象**。

这个不变量是增量垃圾回收的基石。如果它成立，GC 可以安全回收所有白色对象——它们确实不可达。挑战在于在你的代码（修改器）不断修改对象的同时维持这个不变量。这就是**写屏障**的工作。

在本文中，你将学习三色抽象、GC 状态机、三种写屏障、为什么 LuaJIT 对表使用后向屏障、增量步进如何保持暂停短暂，以及保持死键存活的 JIT 友好设计选择。

> **核心要点**
> - 三色不变量（黑色永不指向白色）是增量 GC 正确性的基石。
> - 写屏障检测并修复修改器修改对象时的不变量违反。
> - 表的后向屏障（重新灰色化）比前向屏障（标记值）更便宜。
> - GC 增量运行，以小步骤偿还内存债务。
> - 弱表和终结器在原子阶段处理。

## 三色抽象——基础

LuaJIT 的 GC 使用**三色标记**方案，这是增量垃圾回收的经典技术。每个对象处于三种状态之一：

```
 ┌─────────────────────────────────────────────────────────────┐
 │  白色   │  尚未到达。回收候选。                             │
 │  灰色   │  已到达，但子对象尚未扫描。                        │
 │  黑色   │  已到达且所有子对象已扫描。                        │
 └─────────────────────────────────────────────────────────────┘
```

### 颜色转换

```
 ┌────────┐   标记根     ┌────────┐   扫描子对象    ┌────────┐
 │ 白色   │────────────▶│ 灰色   │───────────────▶│ 黑色   │
 └────────┘             └────────┘                └────────┘
     ▲                                                │
     │              如果仍是白色则回收                    │
              ◀────────────────────────────────────────┘
```

- **白色 → 灰色**：GC 在标记期间到达一个对象
- **灰色 → 黑色**：GC 扫描对象的子对象，将它们标记为灰色
- **白色 →（回收）**：如果对象在标记结束时仍是白色，则不可达

### 两种白色

LuaJIT 使用**两种白色**：`WHITE0`（0x01）和 `WHITE1`（0x02）。任一时刻只有一种是"当前"白色。这让 GC 能区分上一轮存活的对象和新分配的对象：

```c
#define LJ_GC_WHITE0  0x01
#define LJ_GC_WHITE1  0x02
```

每次 GC 周期后，当前白色翻转。上一轮白色的对象现在处于"另一种"白色——如果仍不可达，将在下轮被回收。

### 颜色编码

颜色编码在 `GCHeader` 的 `marked` 字节中：

```c
#define LJ_GC_WHITE0   0x01
#define LJ_GC_WHITE1   0x02
#define LJ_GC_BLACK    0x04
#define LJ_GC_FINALIZED 0x08
#define LJ_GC_WEAKKEY  0x08   /* 共享位 */
#define LJ_GC_WEAKVAL  0x10
#define LJ_GC_FIXED    0x20
#define LJ_GC_SFIXED   0x40
```

对象在**没有白色和黑色位时是灰色**。这是巧妙的编码：灰色是白色和黑色的双重缺失。

## 不变量——黑色永不变白

增量 GC 的根本不变量：

> **黑色对象永远不指向白色对象。**

### 为什么这很重要

如果不变量成立：
- 所有黑色对象都是可达的（它们从根被标记）
- 没有黑色对象指向白色对象
- 因此，白色对象从任何根都不可达
- GC 可以安全回收所有白色对象

如果不变量被违反：
- 黑色对象指向白色对象
- 白色对象是可达的（通过黑色对象）
- 但 GC 认为它不可达（仍是白色）
- **GC 回收一个可达对象 → 崩溃**

### 不变量如何被破坏

在传播阶段，GC 正在把灰色对象变黑。同时，你的 Lua 代码在修改对象：

```lua
local A = {}      -- A 是黑色（已扫描）
local B = {}      -- B 是白色（尚未到达）

A.field = B       -- 黑色对象 A 现在指向白色对象 B！
                  -- 不变量被违反！
```

如果 GC 完成标记时没注意到这个新引用，B 将在仍可通过 A 到达时被回收。

### 修复：写屏障

写屏障检测并修复不变量违反。当黑色对象获得对白色对象的新引用时，屏障触发并恢复不变量。

## GC 状态机——六个阶段

LuaJIT 的 GC 作为状态机运行，有六个阶段：

```
 ┌───────────┐    标记根      ┌─────────────┐    扫描所有灰色   ┌───────────┐
 │ GCSpause  │──────────────▶│ GCSpropagate│──────────────────▶│ GCSatomic │
 │           │               │             │                   │           │
 └───────────┘               └─────────────┘                   └─────┬─────┘
      ▲                                                            │
      │                                                            │ 原子
      │                                                            ▼
      │                                                       ┌───────────┐
      │                                                       │GCSsweep-  │
      │                                                       │string     │
      │                                                       └─────┬─────┘
      │                                                             │
      │                                                             ▼
      │                                                       ┌───────────┐
      │                                                       │ GCSsweep  │
      │                                                       └─────┬─────┘
      │                                                             │
      │                                                             ▼
      │                                                       ┌───────────┐
      │                                                       │GCSfinalize│
      │                                                       └─────┬─────┘
      │                                                             │
      └─────────────────────────────────────────────────────────────┘
                                                                   完成
```

### 阶段 1：GCSpause

周期开始。`gc_mark_start()` 标记所有 GC 根：
- 主线程
- 环境表
- VM 线程
- 注册表
- `gcroot[]` 数组（元方法名称、basemt、I/O、FFI）

然后转换到 GCSpropagate。

### 阶段 2：GCSpropagate

增量标记阶段。`propagatemark()` 从灰色列表弹出一个灰色对象，遍历其子对象（将它们标记为灰色），并将对象变黑。

每种对象类型有不同的遍历：
- **表**：检查 `__mode` 的弱键/值，标记数组 + 哈希部分
- **函数**：标记环境、原型、上值
- **原型**：标记可收集常量、chunkname
- **线程**：标记栈槽，加入 grayagain（永不变黑）
- **追踪**：标记 IR 常量、链接追踪、起始原型
- **用户数据**：立即标记为黑色（永不灰色），标记元表/环境
- **关闭的上值**：立即标记为黑色

此阶段增量运行——每次 `lj_gc_step()` 调用处理少量对象。

### 阶段 3：GCSatomic

原子阶段——**不可中断**。当灰色列表为空时：

1. 重新标记开放的上值（线程可能已死）
2. 传播剩余
3. 处理 grayagain 列表（线程、弱表）
4. 重新标记运行中的线程、当前追踪、GC 根
5. `lj_gc_separateudata()` — 将带 `__gc` 的用户数据移到 mmudata 列表
6. `gc_clearweak()` — 清除弱表中即将被回收的条目
7. **翻转当前白色** — 为下一轮做准备

原子阶段短（有界数量的对象）但不可中断。

### 阶段 4：GCSsweepstring

逐链清扫字符串驻留表。死字符串被释放；存活字符串翻转为当前白色。

### 阶段 5：GCSsweep

清扫所有 GC 对象。死对象通过 `gc_freefunc[]` 分派表释放。存活对象翻转为当前白色。

### 阶段 6：GCSfinalize

为 mmudata 列表中的用户数据/cdata 调用 `__gc` 终结器。终结器通过 `lj_vm_cpcall`（受保护调用）运行。CData 终结器使用单独的 `GCROOT_FFI_FIN` 表。

## 写屏障——检测违反

写屏障是维持黑色永不指向白色不变量的机制。LuaJIT 有三种类型：

### 前向屏障（`lj_gc_barrierf`）

用于非表对象。当黑色对象获得对白色对象的新引用时：

```c
void lj_gc_barrierf(global_State *g, GCobj *o, GCobj *v) {
  if (isblack(o) && iswhite(v)) {
    /* 不变量被违反！修复： */
    if (o->gch.gct == ~LJ_TTAB) {
      /* 表使用后向屏障 */
      lj_gc_barrierback(g, gco2tab(o));
    } else {
      /* 其他对象：标记白色值 */
      reallymarkobject(g, v);
    }
  }
}
```

前向屏障标记白色值（把边界前移）。这是正确的但如果频繁执行会很贵。

### 后向屏障（`lj_gc_barrierback`）

用于表。不标记值，而是把表移回灰色：

```c
void lj_gc_barrierback(global_State *g, GCtab *t) {
  /* 把黑色变回灰色 */
  t->gch.marked &= ~(uint8_t)LJ_GC_BLACK;
  /* 加入 grayagain 列表等待重新扫描 */
  linkgray(g, &t->gch);
}
```

表将在下一轮传播阶段被重新扫描。这更便宜，因为：
- 重新灰色化每次写入 O(1)
- 重新扫描每个 GC 周期发生一次
- 摊销成本低于每次写入都标记

### 上值屏障（`lj_gc_barrieruv`）

专门用于关闭的上值。当上值被关闭（其变量离开作用域）时，屏障确保关闭的值不指向已回收对象。

## 为什么表用后向屏障？

表是 Lua 中被修改最频繁的对象。使用前向屏障需要在每次表赋值时标记值——做百万次表写入时很贵。

```
 前向屏障（昂贵）：                  后向屏障（便宜）：
 ┌──────────┐                        ┌──────────┐
 │  A       │                        │  A       │
 │ (黑色)   │───field──────▶│  B   │  │ (灰色)   │───field──────▶│  B   │
 └──────────┘   标记 B      │(白色)│  └──────────┘   不标记     │(白色)│
                每次写入     └──────┘  稍后重新扫描 A  └──────┘
```

**前向屏障成本**：每次写入 O(1)，但常数因子高（必须遍历并标记值的子对象）。

**后向屏障成本**：每次写入 O(1)（只需翻转一位并链接到 grayagain），加上每个 GC 周期 O(子对象) 的重新扫描。

对于写入频繁的表，后向屏障明显更便宜。标准 Lua 使用前向屏障；LuaJIT 的选择是其性能秘密之一。

## 增量步进——保持暂停短暂

LuaJIT 的 GC 不是一次性运行完。它增量运行，与你的代码交错。

### 步进机制

```c
void lj_gc_step(jit_State *J) {
  MSize steps = (GCSTEPSIZE * J->gc.stepmul) >> 8;
  gc->debt -= steps;
  while (gc->debt > 0 && lj_gc_step(J->g)) {
    /* 持续步进直到债务还清或阶段改变 */
  }
}
```

`lj_gc_step()` 在 `gc.total >= gc.threshold` 时由 `lj_gc_check()` 调用。它推动收集器前进一小步。

### 债务与阈值

- **债务**：`gc.total - gc.threshold` — 超出预算的内存量
- **阈值**：每轮后重新计算为 `(estimate / 100) * pause`
- **步长**：每次调用 `GCSTEPSIZE * stepmul / 256` 单位

```
 内存
  ▲
  │    ┌───┐     ┌───┐
  │    │   │     │   │
  │────┤   ├─────┤   ├──── 阈值
  │    │   │     │   │
  │    └───┘     └───┘
  │    债务       债务被
  │    积累       增量偿还
  └──────────────────────────────────▶ 时间
```

### 调优

```lua
-- 设置暂停时间（默认 100 = 估算值的 100%）
collectgarbage("setpause", 200)  -- 周期间等待更久

-- 设置步进乘数（默认 100 = GCSTEPSIZE 的 100%）
collectgarbage("setstepmul", 200) -- 每步收集更快
```

更高的 `pause` = 周期间隔更长，使用更多内存。更高的 `stepmul` = 收集更快，更多 CPU 时间花在 GC。

## 弱表与终结器

### 弱表

带有 `__mode` 元方法且包含 'k'（弱键）和/或 'v'（弱值）的表：

```lua
local t = {}
setmetatable(t, {__mode = "kv"})  -- 弱键和弱值
```

弱表在原子阶段处理：
1. 传播期间，弱表被加入 `weak` 列表
2. 在 `gc_clearweak()` 中，键/值即将被回收的槽位被清除
3. 字符串永远不是弱引用——它们被标记（比清除槽位更便宜）

### 终结器

带 `__gc` 元方法的用户数据在原子阶段被移到 `mmudata` 列表。在 GCSfinalize 中，它们的终结器通过 `lj_vm_cpcall`（受保护调用）执行。

终结器可以复活对象——如果终结器把对象存到某处，它再次变为可达。LuaJIT 正确处理这种情况。

## 死键——JIT 友好的设计选择

与标准 Lua 5.1 不同，LuaJIT **不销毁表中的死键**。当表中的值被设为 nil 时，键仍保留在哈希表中。

### 为什么？

JIT 编译器基于键模式特化表访问。`HREFK` 指令（已知键的哈希引用）假设如果键存在，其哈希槽是稳定的。销毁死键会破坏这个假设。

```lua
-- LuaJIT 可以特化这个：
t.foo = 1
print(t.foo)  -- HREFK：知道 "foo" 在特定槽位

t.foo = nil   -- 标准 Lua：从哈希中移除 "foo"
              -- LuaJIT：把 "foo" 留在哈希中（死键）
```

### 权衡

- **标准 Lua**：销毁死键 → 更少内存，但哈希槽不稳定
- **LuaJIT**：保留死键 → 稍多内存，但哈希槽稳定 → JIT 代码更快

对多数应用，内存开销与稳定哈希槽带来的性能增益相比可以忽略不计。

## 常见问题解答

### 为什么有两种白色？

为了区分上一轮存活的对象和新分配的对象。每次 GC 周期后，当前白色翻转。上一轮白色的对象现在处于"另一种"白色——如果仍不可达，将在下轮被回收。这避免了在所有存活对象上清除标记。

### 如果省略写屏障会怎样？

GC 可能回收一个可达对象。如果黑色对象指向 GC 不知道的白色对象，白色对象会被释放。任何后续访问都是释放后使用 → 崩溃或损坏。

### GC 能在增量回收期间耗尽内存吗？

能。如果分配速率超过回收速率，内存使用会无限增长。GC 最终会进入"恐慌"模式，更积极地运行。调整 `setpause` 和 `setstepmul` 可以帮忙。

### 如何调优 GC？

```lua
collectgarbage("setpause", 200)   -- 估算值的 200%（等更久）
collectgarbage("setstepmul", 400) -- GCSTEPSIZE 的 400%（收集更快）
```

更高的 pause = 周期间隔更长，更多内存。更高的 stepmul = 收集更快，更多 CPU。

### 为什么字符串永远不是弱引用？

字符串被驻留——相同字符串共享同一对象。如果弱表中的字符串键被回收，所有对该字符串的引用都会失效。相反，LuaJIT 在 GC 期间标记字符串（永远不作为弱引用回收），这比清除槽位更便宜。
