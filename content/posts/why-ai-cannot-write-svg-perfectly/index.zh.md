## 引言

我原本有一个简单的任务：验证博客中全部 155 个外部链接是否仍然可用。一次快速的 `curl` 扫描标记出 130 个"失效"链接——33% 的失效率。这本应是一个下午就能完成的例行修复。结果，它变成了一场为期一周的调查，对象是互联网上最被低估的复杂文件格式之一：SVG。

第一个异常信号让我意识到事情没那么简单：许多"失效"链接指向的是 OECD、Morningstar、McKinsey 这样维护良好的一线网站。这些站点并没有宕机。它们只是拒绝与我的 AI Agent 对话。但当我深入探究访问这些受保护站点所需的工具和技术时，我发现了一个更根本的问题——博客中的 SVG 图表本身就充满了缺陷。

饼图的扇形之间有明显间隙。文字标签与数据线重叠。颜色在图表中多次出现。柱状图的负值"飘"在基线上方。

我无意间撞上了 AI 最顽固的盲区之一：生成完美的 SVG 代码。

本文讲述了我在 AI 为什么无法完美编写 SVG 这一课题上学到的东西。它基于对 155 个 SVG 图表的第一手审计经验、修复数十张损坏图片的实践，以及针对 SVG 生成失败技术原因的研究。无论你是在构建生成图形的 AI Agent，还是只是想创建更好的图表，理解这些局限性都将为你节省数小时的调试时间。

<!-- more -->

> **核心要点**
> - **SVG 看似简单，实则隐藏复杂性** — W3C SVG 2 规范包含 16 章正文加 11 个附录
> - **stroke-dasharray 陷阱** — 即使数学上正确的值，也可能因浮点精度导致可见间隙

> - **七大根因** — 从坐标系混淆到根本性的视觉验证鸿沟
> - **path 渲染是解决方案** — 使用 SVG `<path>` 元素的弧线命令可确保完美拼接

## 审计 155 个 SVG 图表的那一天

一切从一个简单的 bash 循环开始：

```bash
for url in $(cat all-links.txt); do
  code=$(curl -sI -o /dev/null -w "%{http_code}" --max-time 10 "$url")
  echo "$code  $url"
done
```

结果：215 个链接返回 200（正常），47 个返回 301/302（重定向），130 个返回 403（禁止访问）或 000（超时）。但当我抽查几个"失效"链接时，发现了异常：在普通浏览器中打开它们完全正常。页面存在，只是不想跟 `curl` 说话。

当我研究机器人检测机制（TLS 指纹、浏览器指纹、行为分析、IP 信誉）时，我意识到自己需要生成验证图表来记录发现。正是在那时，我发现了真正的问题：我正在生成的 SVG 图表也有缺陷。

饼图的扇形之间有可见间隙。文字标签与折线图的预测线重叠。颜色多次出现。柱状图中负值"飘"在空中。

我偶然发现了 AI 最顽固的盲区之一：生成完美的 SVG 代码。

## stroke-dasharray 陷阱

我遇到的最常见且最难诊断的错误，是使用 `stroke-dasharray` 绘制饼图时弧长计算不正确。

### stroke-dasharray 的工作原理

`stroke-dasharray` 属性控制笔触的虚实模式。对于圆形，可以用它来绘制弧形段：

```xml
<circle r="120" stroke="#f97316" stroke-width="40"
        stroke-dasharray="301.6 753.98"
        transform="rotate(-90)" />
```

这里，`301.6` 是实线长度（圆周长的 40%），`753.98` 是间距（完整圆周长）。模式重复：实线 301.6px，间距 753.98px，实线 301.6px，依此类推。

### 为什么"正确"的值也会产生间隙

半径 120 的圆的周长是 `2 × π × 120 ≈ 753.98`。当你叠加多个圆形来创建环形图时，每个圆形绘制一段。问题是浮点精度误差会在多个圆形之间累积。

即使弧长在数学上是正确的，渲染引擎也可能在段边界处产生微小间隙。当以下情况时，这些间隙尤其明显：

- 间距值与圆周长不完全匹配
- 多个圆形以不同旋转角度叠加
- 抗锯齿与亚像素坐标相互作用

## AI 生成的五类 SVG 错误

基于对 155 个 SVG 图表的审计，我将问题归纳为五种不同类型：

### 1. 几何计算错误

**饼图间隙**是最常见的几何错误。发生在以下情况：
- 弧长之和不等于圆周长
- 旋转角度计算错误
- stroke-dasharray 间距值不一致

**柱状图基线未对齐**是另一个常见问题。负值柱形应从零基线开始向下延伸，但 AI 经常错误计算 `y` 位置，导致柱形"飘"在基线上方。

```xml
<!-- 错误：柱形从基线下方开始 -->
<rect y="218.9" width="40" height="81.1" ... />

<!-- 正确：柱形从基线开始 -->
<rect y="195" width="40" height="141.1" ... />
```

### 2. 文字溢出和重叠

文字元素经常超出 viewBox 边界或与其他元素重叠：

- 标签位于 `x=605`，而 `viewBox="0 0 640 380"`，超出右边缘
- 数据标签与图表线条或柱形重叠
- 图例文字与图表区域碰撞

### 3. 颜色重复

AI 有时会为不同类别分配相同或相似的颜色，使其难以区分。一个特别隐蔽的变体：使用扇区颜色作为中心文字颜色，使该颜色看起来出现了多次。

### 4. 基线未对齐

在有负值的柱状图中，零基线必须明确定义。AI 经常错误计算负值柱形的 `y` 坐标：

```xml
<!-- 错误：y 位置在基线下方 -->
<rect y="218.9" height="81.1" ... />

<!-- 正确：y 位置等于基线 -->
<rect y="195" height="141.1" ... />
```

### 5. 字体和渲染问题

当 SVG 转换为 PNG 时，如果目标系统缺少所需字体，文字可能显示为方块（□□□）。这在中文文字和自定义字体中尤为常见。

## AI 为什么在 SVG 上犯错——技术分析与研究

通过研究和第一手经验，我识别出七个根本原因，解释 AI 为什么在 SVG 生成上举步维艰。

### 根因一：SVG 规范复杂度

W3C SVG 2 规范体量庞大——**16 章正文加 11 个附录**，涵盖：

- **路径数据语法**使用前缀表示法，单字符命令分绝对（大写）和相对（小写）两种形式。命令可以连锁重复字母，空格可以省略——形成密集、模糊的标记流。
- **贝塞尔曲线**需要理解描述斜率的控制点，包括三次（`C`）、光滑三次（`S`）、二次（`Q`）和光滑二次（`T`）变体。
- **椭圆弧命令**（`A`）接受 **7 个参数**：`rx ry x-axis-rotation large-arc-flag sweep-flag x y`。对于任意两个点和半径，有 **四个数学上有效的弧**，两个布尔标志从中选择。这被广泛认为是最难的 SVG 命令。

规范明确指出"不建议使用 XML 编辑器或文本编辑器创建复杂路径"——然而这正是 AI 模型试图做的事情。

### 根因二：坐标系混淆

SVG 使用**Y 轴向下的坐标系**，与标准数学约定根本不同：

| 属性 | 标准数学 | SVG |
|------|---------|-----|
| Y 轴方向 | 向上为正 | **向下为正** |
| 原点 | 通常在中心 | **左上角** |
| 角度方向 | 逆时针 | **顺时针** |
| 0° 角 | 右（3 点钟） | 右（3 点钟） |

因为 Y 轴翻转，**正角度顺时针旋转**——与数学家和大多数编程框架的预期相反。在数学文本和代码上训练的 AI 模型必须主动抑制其习得的直觉，才能生成正确的 SVG。

### 根因三：浮点精度

LLM 逐标记生成数值，没有真正的算术计算能力。它们无法可靠地：

- 跟踪长 SVG 文件中的精度需求
- 四舍五入数值以最小化累积误差
- 基于精度需求在 `transform="matrix(...)"` 和链式变换之间做出选择

当多个 SVG 变换通过嵌套的 `<g>` 元素链式连接时，**误差随每次乘法累积**。这导致动画中的可见漂移和复杂图表中的错位。

### 根因四：视觉验证鸿沟

这是最根本的局限性：**LLM 以文本方式生成代码，但无法感知视觉渲染输出。**

与生成 Python 函数（单元测试可验证正确性）或写作散文（语义连贯性可自我评估）不同，SVG 生成具有：

- **无文本自我验证**：你无法"阅读"SVG 路径并知道它看起来像什么，不渲染不行
- **无单元测试**：没有 `assert(svg_looks_correct())` 函数
- **空间推理需求**：判断元素是否重叠、对齐或成比例需要视觉处理
- **审美判断**："这好看吗？"本质上是视觉的

这就是为什么最有前景的研究方法（DiffSketcher、Design2Code、SiD2C）都采用**渲染反馈循环**——使用可微分光栅化器或多模态视觉，赋予 AI 某种形式的"视觉"。

### 根因五：上下文窗口限制

详细的 SVG 文件可能非常长，占用大量上下文窗口空间。"迷失在中间"现象研究表明，LLM 在长上下文中间位置的信息理解能力下降。对于 SVG 生成，这表现为：

- **坐标系不一致**：模型忘记开头建立的 viewBox
- **变换漂移**：嵌套变换丢失累积状态跟踪
- **样式不一致**：早期定义的填充/笔触属性后来被遗忘
- **ID/引用断裂**：`clip-path="url(#myClip)"` 引用了被截断的定义

### 根因六：训练数据偏差

来自网络的 SVG 训练数据严重偏向：

- **简单图标**：Material Design 图标、Font Awesome、UI 元素
- **模板生成的 SVG**：来自 Inkscape、Figma 和 Illustrator 的输出，格式冗长、机器友好

与此同时，复杂插图、弧线命令、精确几何构造和手工优化的 SVG 代表性不足。这导致模型默认使用简单形状，避免弧线命令。

### 根因七：视觉输出无单元测试

没有自动化方法可以在不人工检查的情况下验证 SVG 是否正确。这造成了文本代码生成不存在的根本性质量保证问题。

## Path 渲染解决方案

经过广泛测试，我发现使用带弧线命令的 SVG `<path>` 元素是绘制饼图最可靠的方法。这种方法确保完美拼接，无间隙。

### Path 饼图背后的数学

对于从角度 A1 到 A2 的环形段（从 12 点方向顺时针测量）：

```
M x1 y1           // 移动到外弧起点
A R R 0 0 1 x2 y2 // 绘制外弧到终点
L x3 y3           // 连接到内弧起点
A r r 0 0 0 x4 y4 // 绘制内弧回到起点
Z                 // 闭合路径
```

其中：
- `x1 = cx + R × sin(A1)`, `y1 = cy - R × cos(A1)` — 外弧起点
- `x2 = cx + R × sin(A2)`, `y2 = cy - R × cos(A2)` — 外弧终点
- `x3 = cx + r × sin(A2)`, `y3 = cy - r × cos(A2)` — 内弧起点
- `x4 = cx + r × sin(A1)`, `y4 = cy - r × cos(A1)` — 内弧终点

### Python 实现

```python
import math

def pie_slice_path(cx, cy, R, r, angle_start, angle_end):
    """生成环形段的 SVG 路径。
    角度从 12 点方向顺时针测量（度）。"""
    a1 = math.radians(angle_start)
    a2 = math.radians(angle_end)

    # 外弧起点/终点
    x1 = cx + R * math.sin(a1)
    y1 = cy - R * math.cos(a1)
    x2 = cx + R * math.sin(a2)
    y2 = cy - R * math.cos(a2)

    # 内弧起点/终点
    x3 = cx + r * math.sin(a2)
    y3 = cy - r * math.cos(a2)
    x4 = cx + r * math.sin(a1)
    y4 = cy - r * math.cos(a1)

    # large-arc 标志：< 180° 为 0，≥ 180° 为 1
    span = (angle_end - angle_start) % 360
    large_arc = 1 if span > 180 else 0

    return (f"M {x1:.2f} {y1:.2f} "
            f"A {R} {R} 0 {large_arc} 1 {x2:.2f} {y2:.2f} "
            f"L {x3:.2f} {y3:.2f} "
            f"A {r} {r} 0 {large_arc} 0 {x4:.2f} {y4:.2f} Z")
```

### 为什么这有效

- 每个段是单一的闭合路径——不可能有间隙
- 相邻段共享精确的边界坐标
- 没有跨多个元素的浮点累积
- 在所有 SVG 渲染器中可靠工作

## 系统化 SVG 质量检查清单

基于我的经验，以下是验证 AI 生成 SVG 的综合清单：

### XML 有效性
- [ ] `xmllint --noout` 通过（无 XML 错误）
- [ ] 存在 `xmlns="http://www.w3.org/2000/svg"`
- [ ] 无裸 `&` — 全部转义为 `&amp;`

### 几何
- [ ] 饼图/环形图：使用 `<path>` 元素（非 stroke-dasharray）
- [ ] 所有段完美拼接，无间隙
- [ ] 柱状图：负值柱从基线开始
- [ ] 所有坐标用三角函数计算（非猜测）

### 文字
- [ ] 无文字超出 viewBox 边界
- [ ] 文字不与图表元素重叠
- [ ] 字体族在目标系统上可用
- [ ] 字体大小可读（≥ 9px）

### 颜色
- [ ] 每个类别有独特、可区分的颜色
- [ ] 中心文字颜色不与任何扇区匹配
- [ ] 颜色对比度足够

### 视觉检查
- [ ] 转换为 PNG 并在 100% 缩放下检查
- [ ] 检查亮色和暗色主题
- [ ] 验证不同缩放级别

## 常见问题

### AI 能生成完美的 SVG 吗？

**目前不能。** AI 可以生成语法正确、遵循规范的 SVG，但确保视觉完美需要渲染和检查，这是纯文本模型无法做到的。视觉验证鸿沟是根本性局限。

### 绘制饼图的最佳 SVG 方式是什么？

使用带弧线命令（`A`）的 `<path>` 元素。避免使用 `stroke-dasharray` 叠加多个圆形——即使数学上正确的值也可能因浮点精度产生可见间隙。

### 如何验证 AI 生成的 SVG？

1. 运行 `xmllint --noout` 检查 XML 有效性
2. 用 `rsvg-convert` 转换为 PNG 并目视检查
3. 用上面的清单检查几何
4. 在亮色和暗色主题下测试

### 为什么我的饼图有间隙？

最常见的原因是 `stroke-dasharray` 间距值不正确。间距应等于圆周长（`2πr`），但即使如此，浮点精度也可能导致间隙。切换到 path 渲染以获得无间隙保证。

### 哪些工具有助于 SVG 质量？

- `xmllint` — XML 有效性检查
- `rsvg-convert`（librsvg）— SVG 转 PNG
- `puppeteer` / Playwright — 浏览器渲染
- Python 脚本 — 坐标计算和验证

## 结论

AI 在 SVG 上的挣扎不是单一问题——它是规范复杂度、坐标系混淆、浮点精度和无法看到渲染输出的根本性无能共同形成的完美风暴。

视觉验证鸿沟是最难解决的。即使一个模型拥有完美的 SVG 规范知识、无限的上下文和无可挑剔的算术能力，它仍然在"盲目"地生成几何图形。没有渲染和检查其输出的能力，它就无法闭合意图与结果之间的循环。

目前，最佳方法是：
1. **Path 渲染**绘制饼图（保证无间隙）
2. **系统化清单**覆盖常见错误类型
3. **自动化验证**（xmllint + PNG 转换）
4. **人工视觉检查**作为最终质量关卡

AI 可以接近——非常接近——但完美的 SVG 生成仍然是人在回路的过程。
