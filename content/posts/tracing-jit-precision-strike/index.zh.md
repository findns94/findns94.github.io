V8 的 TurboFan 编译整个函数。Java 的 C2 把整个方法编译成机器码。JavaScriptCore 的 DFG 拿完整的基本块做转换。这些都是**方法 JIT**——它们看到函数的全部控制流图，然后优化全部。

LuaJIT 做的则完全不同。它不编译函数，它编译**路径**——程序实际执行过的一条线性指令序列。如果一个循环跑了 100 次，LuaJIT 不会把循环体编译一次；它记录这 100 次迭代中实际走到的那条路径，然后编译那条路径。

这就是「精准打击」哲学：不是用优化地毯式轰炸整个函数，而是用狙击子弹精准命中真正重要的代码。对于合适的工作负载，这意味着更快的启动速度、更紧凑的代码、以及对真正决定运行时的热路径更好的性能。

在本文中，你将完整学习追踪式 JIT 如何工作——从热路径检测到录制、编译、执行、去优化。我们将追踪完整流水线，看这种方法为何对 Lua 这类动态语言如此有效。

> **核心要点**
> - 追踪式 JIT 录制一条热**路径**（线性追踪），而非整个函数——这是与方法 JIT 的根本设计差异。
> - 类型特化自然发生：追踪记录运行时实际观察到的类型，守卫（guard）在每次执行时验证它们。
> - 编译后的机器码存在于 `mmap` 分配的内存缓冲区中，通过 `mprotect` 切换为可执行权限，作为函数指针调用。
> - 基于快照的去优化让激进的推测执行变得安全——守卫失败时重建解释器状态并恢复执行。
> - 侧追踪构建**追踪树**，覆盖同一代码的多条路径，每条都被编译并链接在一起。

## 两种哲学——方法 JIT vs 追踪式 JIT

每个 JIT 编译器都面对同一个问题：我编译什么？答案定义了 JIT 设计的两大学派。

**方法 JIT**（V8 TurboFan、Java C2、JavaScriptCore DFG/FTL、.NET RyuJIT）的回答是：「编译整个函数。」编译器拿到函数字节码，构建覆盖所有基本块和分支的控制流图（CFG），对整个图做优化，然后为整个函数发射机器码。函数的每条路径都得到编译后的代码。

**追踪式 JIT**（LuaJIT、TraceMonkey、PyPy、Dynamo）的回答是：「编译刚跑过的那条路径。」编译器等到循环或函数入口变热，然后记录实际执行的精确指令序列——包括走了哪个分支、观察到什么类型、调用了哪个函数。只编译那一条线性序列。

```
 方法 JIT（地毯式轰炸）：              追踪式 JIT（精准打击）：

 ┌─────────────────────┐                ┌─────────────────────┐
 │  ┌───┐   ┌───┐      │                │  ┌───┐   ┌───┐      │
 │  │ A ├──▶│ B │      │                │  │ A ├──▶│ B │      │
 │  └─┬─┘   └─┬─┘      │                │  └─┬─┘   └─┬─┘      │
 │    ▼       ▼        │                │    ▼       ▼        │
 │  ┌───┐   ┌───┐      │                │  ┌───┐   ┌───┐      │
 │  │ C │   │ D │      │                │  │ C │   │ D │      │
 │  └─┬─┘   └─┬─┘      │                │  └─┬─┘   └─┬─┘      │
 │    ▼       ▼        │                │    ▼       ▼        │
 │  ┌───┐   ┌───┐      │                │  ┌───┐   ┌───┐      │
 │  │ E │   │ F │      │                │  │ E │   │ F │      │
 │  └───┘   └───┘      │                │  └───┘   └───┘      │
 │                     │                │                     │
 │  所有基本块都被编译    │                │  只编译 A→B→D→F    │
 │  （整个控制流图）      │                │  （一条路径）        │
 └─────────────────────┘                └─────────────────────┘
```

这是覆盖范围与精度的权衡：

| 方面 | 方法 JIT | 追踪式 JIT |
|------|---------|-----------|
| 编译单元 | 整个函数 | 单条热路径 |
| 优化范围 | 完整控制流图 | 线性追踪 |
| 预热速度 | 较慢（编译全部） | 较快（只编译热代码） |
| 峰值性能 | 更高（全函数优化） | 单追踪较低，但追踪本身极紧凑 |
| 类型特化 | 推测式，失配时去优化 | 观察到的类型，守卫验证 |
| 最适合 | 静态语言、复杂方法 | 动态语言、紧密循环 |
| 内存占用 | 较高（全部代码被编译） | 较低（仅热路径） |

历史上，追踪式 JIT 由 Dynamo（2000）开创——一个透明动态优化系统，录制原生代码中的热路径。Mozilla 的 TraceMonkey（2009）将其引入 JavaScript，在某些基准测试上实现了 2-20 倍加速，随后被方法 JIT 取代。LuaJIT 2（2010+）用 SSA IR、基于快照的去优化和追踪树精炼了这一方法——至今仍是追踪式 JIT 性能的标杆。

## LuaJIT 如何检测热路径

追踪式 JIT 从一个简单问题开始：哪些代码热到值得编译？LuaJIT 的答案是**热计数器**——嵌入解释器循环的执行计数器，每次经过循环头或函数入口时递减。

### 热计数器机制

每个循环操作码（`FORL`、`ITERL`、`LOOP`）和函数入口操作码（`FUNCF`、`FUNCF`）在解释器中都有对应的热计数器。默认阈值是 **56 次迭代**——可通过 `jit.opt.start('hotloop')` 调整。

这个机制存在于 DynASM 生成的解释器（`src/vm_x64.dasc`）中：

```asm
|->forl:                    ; 数值 FOR 循环头
|  sub [hotcount], 1        ; 热计数器递减
|  jg >1                   ; 如果计数器 > 0，跳过 JIT 检查
|  call lj_trace_hot       ; 计数器归零——触发 JIT
|  jmp >2                  ; 继续执行循环体
|1:                        ; 还不够热——运行解释器
|  ...                     ; 实际的 FOR 循环逻辑
|2:                        ; JIT 检查后的落入点
```

当计数器归零，`lj_trace_hot()` 被调用。这个函数将 JIT 状态机从 IDLE 转换到 START，分配一个新的追踪编号，开始录制。

### 追踪状态机

```
 ┌────────┐    hot counter=0    ┌─────────┐    录制中    ┌──────────┐
 │  IDLE  │────────────────────▶│  START  │────────────▶│ RECORD   │
 │        │                     │         │             │          │
 └────────┘                     └─────────┘             └────┬─────┘
      ▲                                                      │
      │                                                      │ 追踪结束
      │                                                      ▼
      │                                                ┌──────────┐
      │ 追踪完成                                        │   END    │
      │◀───────────────────────────────────────────────│          │
      │                                                └────┬─────┘
      │                                                     │ 优化
      │                                                     ▼
      │                                                ┌──────────┐
      └────────────────────────────────────────────────│   ASM    │
                                                       │（编译）   │
                                                       └──────────┘
```

各状态：
- **IDLE**：解释器正常运行，热计数器递减。
- **START**：`lj_trace_hot()` 触发，分配追踪，设置录制器。
- **RECORD**：`lj_record_ins()` 运行，将字节码翻译为 SSA IR。
- **END**：录制停止，追踪被链接，运行优化。
- **ASM**：发射器将机器码写入 mmap 分配的缓冲区。

### I-前缀操作码：桥梁

LuaJIT 的解释器有两套循环和函数操作码：普通版本（`FORL`、`FUNCF`）和 **I-前缀**版本（`IFORL`、`IFUNCF`）。`I` 版本在追踪编译完成后由 JIT 修补——它们与录制器协作，而非运行完整的解释器逻辑。

这是解释器与 JIT 之间的桥梁：相同的字节码，但操作码实现不同——取决于是否存在已编译的追踪。

## 录制一条追踪——字节码到 SSA IR

录制开始后，每条字节码指令都经过 `lj_record_ins()`——一个 2982 行的主调度器，将字节码操作翻译为**SSA（静态单赋值）中间表示**。

### 录制循环

```c
// lj_record_ins() 的简化视图
void lj_record_ins(jit_State *J) {
  BCIns *pc = J->pc;           // 当前字节码位置
  BCOp op = bc_op(*pc);        // 当前操作码

  switch (op) {
    case BC_KSHORT: record_kshort(J, pc); break;
    case BC_ISNUM:  record_isnum(J, pc); break;   // 类型守卫
    case BC_TGETV:  record_tgetv(J, pc); break;   // 表获取
    case BC_ADDVV:  record_addvv(J, pc); break;   // 加法
    case BC_FORL:   record_forl(J, pc); break;    // 循环
    // ... 约 90 个操作码
  }
}
```

每个 `record_*` 函数通过 `emitir()` 宏发射一条或多条 IR 指令：

```c
#define emitir(ot, a, b)  (lj_ir_set(J, (ot), (a), (b)), lj_opt_fold(J))
```

这做两件事：发射 IR 指令，然后立即对它运行 **FOLD 引擎**进行常量折叠和化简。

### 守卫驱动的类型特化

追踪式 JIT 性能的关键是**类型特化**。在 Lua 这类动态语言中，一个变量可以持有数字、字符串、表或函数。方法 JIT 必须生成处理所有可能性的代码（或推测后去优化）。追踪式 JIT 记录实际观察到的类型，并发射一条**守卫**——一个运行时检查，验证这个假设。

```lua
-- Lua 源码
local x = 0
for i = 1, 100 do
  x = x + i    -- x 和 i 在这里都是数字
end
```

`x = x + i` 的录制 IR（简化）：

```
 ─┬──────────────────────────────────────────────────────────────
 │  [1] ISEQ i, ┬──┬        ; 守卫：i 是数字
 │              │  │
 │ [2] FLOAD x, ┼──┼──┬     ; 从栈槽加载 x
 │              │  │  │
 │ [3] ADD   [2], ┼──┼──┬   ; x + i（已知都是数字）
 │                │  │  │
 │ [4] FSTORE x, ─┴──┴──┴   ; 存结果回 x
 ─┴──────────────────────────────────────────────────────────────
```

`ISEQ` 指令是守卫——它检查 `i` 确实是数字。如果检查失败，追踪退出并去优化。如果通过，`ADD` 指令可以用单条 `addsd`（标量浮点加）指令，而非完整的多态加法。

### 录制时的即时优化

录制器不只是翻译——它边录制边优化。每条发射的指令都经过 FOLD 引擎，应用：

- **常量折叠**：`ADD(KNUM 3, KNUM 4)` → `KNUM 7`（录制时计算）
- **代数化简**：`ADD(x, 0)` → `x`；`MUL(x, 1)` → `x`
- **加载前递（FWD）**：如果一个值刚被存储就被加载，跳过内存访问
- **死存储消除（DSE）**：如果存储永远不被读取，删除它
- **窄化（NARROW）**：如果双精度保证是整数，窄化为 int32

这些优化**在录制期间**发生，而非之后。这很不寻常——大多数编译器把录制/翻译和优化分开。但对追踪式 JIT 来说，录制阶段有完美的类型信息（来自守卫），所以立即优化产生最紧凑的 IR。

```
 字节码          录制中                即时优化                  最终 IR
 ──────          ──────                ──────                   ──────
 FORI  ──────▶  guard(i:int)  ──────▶  （折叠常量）   ──────▶  guard(i:int)
 TGETV ──────▶  tgetv(tab,key) ──────▶  （前递加载）   ──────▶  tgetv → 已知偏移
 ADDVV ──────▶  add(x,y)     ──────▶  （窄化为整）   ──────▶  add_i32(x,y)
 FORL  ──────▶  loop_exit?   ──────▶  （消除死存储） ──────▶  loop_link
```

## 追踪链接与侧追踪——构建追踪树

追踪不是孤立存在的。录制停止时，LuaJIT 决定接下来发生什么——这个决定塑造了追踪与其他追踪的关系。

### 追踪结束条件

录制在以下情况停止：
1. **循环回边**：追踪回到它开始的循环头 → `LJ_TRLINK_LOOP`（追踪循环回自身）
2. **守卫失败**：录制期间守卫失败 → `LJ_TRLINK_INTERP`（退出到解释器）
3. **函数返回**：追踪到达 return → `LJ_TRLINK_RETURN`
4. **尾调用**：追踪到达尾调用 → `LJ_TRLINK_TAILREC`
5. **调用**：追踪到达函数调用 → `LJ_TRLINK_STITCH`（追踪拼接）

最常见的情况是循环回边：追踪录制循环的一次完整迭代，然后链接回自己的起点。后续迭代运行编译后的追踪而非解释器。

### 侧追踪：覆盖多条路径

单条追踪覆盖循环的一条路径。但真实代码有分支——追踪的守卫在运行时失败会怎样？LuaJIT 不会立即回退到解释器，而是可以启动一条**侧追踪**，录制另一条路径。

```
                    ┌─────────────────────┐
                    │   父追踪             │
                    │   （主循环路径）       │
                    │                     │
                    │  guard(x > 0) ──────┼────┐ 守卫失败
                    │  ...                │    │ (x <= 0)
                    │  循环回边 ───────────┼─┐  │
                    └─────────────────────┘ │  │
                             ▲              │  │
                             │              │  ▼
                             │     ┌─────────────────────┐
                             │     │   侧追踪 1           │
                             │     │   (x <= 0 路径)     │
                             │     │                     │
                             │     │  handle_negative()  │
                             │     │  退出到解释器        │
                             │     └─────────────────────┘
                             │
                             │     ┌─────────────────────┐
                             │     │   侧追踪 2           │
                             │     │   （类型失配）       │
                             │     │                     │
                             │     │  handle_string()    │
                             │     │  退出到解释器        │
                             │     └─────────────────────┘
                             │
                    （循环回到父追踪）
```

当守卫失败足够多次（默认 10 次，可通过 `jit.opt.start('hotexit')` 调整），`trace_hotside()` 从该退出点的解释器状态开始新的录制。新的侧追踪被编译并**链接**到父追踪：`lj_asm_patchexit()` 修补父追踪的退出桩，让它直接跳转到侧追踪，而非返回解释器。

结果是一棵**追踪树**——覆盖同一循环多条路径的编译追踪树。根追踪处理常见情况；侧追踪处理不太常见的替代路径。

### 追踪拼接

调用追踪的特殊链接类型：当追踪 A 调用的函数变热并编译为追踪 B 时，B 被「拼接」——A 的退出被修补为直接跳转到 B，避免了解释器往返。A 的 `link` 字段被设为 B 的追踪编号。

### 追踪爆炸与黑名单

追踪树的代价：如果循环有很多分支，每个分支点都能产生侧追踪，每个侧追踪又能产生自己的侧追踪。这种**追踪爆炸**会消耗大量内存。

LuaJIT 通过**黑名单**缓解：如果某个字节码位置导致反复去优化（超过阈值次数），LuaJIT 停止追踪它。该位置被标记为「不可追踪」，永远由解释器处理。这防止了病态情况——JIT 浪费时间去编译立即失败的追踪。

## 基于快照的去优化的安全网

追踪式 JIT 的激进优化依赖**推测**：追踪假设类型、分支方向、调用目标基于录制时观察到的值。假设成立时，追踪全速运行。假设不成立时，追踪必须**去优化**——退出编译代码，恢复解释器执行。

### 守卫即推测断言

追踪中的每条守卫都是推测性断言。守卫检查一个条件（类型、边界、真假），要么继续，要么退出：

```asm
; 编译后的追踪代码（x86-64）
movsd xmm0, [rbx+8]      ; 加载 x
ucomisd xmm0, xmm0        ; 检查 NaN（是合法 double 吗？）
jp .exit_guard_3          ; 如果是 NaN，跳到退出桩
; ... 继续追踪 ...
```

`jp .exit_guard_3` 是守卫的退出路径。如果条件失败，执行跳转到**退出桩**——一小段保存当前状态并调用退出处理器的代码。

### 退出处理器与状态重建

守卫失败时：

```
 ┌──────────┐    守卫失败    ┌──────────────┐    填充状态    ┌──────────────┐
 │  追踪    │──────────────▶│   退出桩     │─────────────▶│  退出处理器   │
 │（原生码） │              │（每个守卫一个）│              │（lj_vm_exit_ │
 └──────────┘              └──────────────┘              │  handler）   │
                                                         └──────┬───────┘
                                                                │
                                                                ▼
                                                         ┌──────────────┐
                                                         │ lj_snap_     │
                                                         │ restore()    │
                                                         │ 重建解释器   │
                                                         │ 状态         │
                                                         └──────┬───────┘
                                                                │
                                                                ▼
                                                         ┌──────────────┐
                                                         │  解释器      │
                                                         │  从恢复的 PC │
                                                         │  恢复执行    │
                                                         └──────────────┘
```

1. **退出桩**将所有寄存器和溢出槽值保存到 `ExitState` 结构
2. **`lj_vm_exit_handler`**（汇编编写）接收退出编号和寄存器状态
3. **`lj_trace_exit()`** → `trace_exit_cp()` 查找该退出的快照
4. **`lj_snap_restore()`** 从快照重建解释器状态

### 快照结构

快照存在于追踪的每个守卫点。它记录：

- 哪个栈槽持有哪个 IR 引用
- 调用帧链（每个活跃函数的 PC + 帧链接）
- 机器码偏移量（让退出处理器知道哪个守卫失败）

```c
typedef struct SnapShot {
  uint32_t mapofs;    // 快照映射的偏移量
  IRRef1 ref;         // 该快照的第一个 IR 引用
  uint16_t mcofs;     // 机器码中的偏移量
  uint8_t nslots;     // 有效槽位数
  uint8_t topslot;    // 最大帧范围
  uint8_t nent;       // 压缩条目数
  uint8_t count;      // 已取退出次数
} SnapShot;

typedef uint32_t SnapEntry;  // 打包：slot(8) | flags(8) | ref(16)
```

每个 `SnapEntry` 编码 `(slot << 24) + flags + ref`，其中 flags 指示该槽是帧指针、延续、还是无需恢复。

### 为什么这很重要

基于快照的去优化让追踪式 JIT 的激进优化变得**安全**。追踪可以假设类型恒定、分支总走一个方向、调用目标不变——因为如果任何假设失败，快照提供了在该精确点的解释器状态的精确定位。

这与方法 JIT 的去优化（栈上替换，OSR）有本质不同，后者必须从完整 CFG 重建状态。追踪式 JIT 的快照更简单，因为追踪是线性的——每个点只有一种可能的状态。

## JIT 如何真正执行机器码

这是一切成为现实的机制：编译后的追踪如何真正运行？答案涉及操作系统的内存管理——`mmap` 和 `mprotect`。

### MCode 分配流水线

LuaJIT 的 JIT 分配器（`lj_mcode.c`）管理称为 **MCode 区域**的内存区（默认每个 64KB，总计最多 2MB）。流水线：

```
 第 1 步：mmap(RW)           第 2 步：汇编            第 3 步：mprotect(RX)
┌──────────────────┐      ┌──────────────────┐      ┌──────────────────┐
│                  │      │  lj_asm.c 写入   │      │                  │
│  RW 页           │─────▶│  x86-64 字节     │─────▶│  RX 页           │
│  （读-写）        │      │  到缓冲区        │      │  （读-执行）     │
│                  │      │                  │      │                  │
└──────────────────┘      └──────────────────┘      └──────────────────┘
        │                                                   │
        │                                                   ▼
        │                                          第 4 步：调用
        │                                          ┌──────────────────┐
        │                                          │  转换为函数指针  │
        └─────────────────────────────────────────▶│  fn(T)           │
                                                   └──────────────────┘
```

**第 1 步——分配 RW 内存：**
```c
// 来自 lj_mcode.c — 简化
void *mcode_allocarea(jit_State *J, MSize sz) {
  void *p = mmap(NULL, sz, PROT_READ | PROT_WRITE,
                 MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
  // p 现在是 RW 内存区域——可以写入，但不能执行
  return p;
}
```

带 `PROT_READ | PROT_WRITE` 的 `mmap` 分配可写但**不可执行**的内存页。这是 W^X（写异或执行）安全原则：内存从不同时可写且可执行。

**第 2 步——写入机器码：**
```c
// 来自 lj_asm.c —— 发射器向 MCode 缓冲区写字节
void lj_asm_trace(jit_State *J, GCtrace *T) {
  MCode *mcarea = lj_mcode_reserve(J, &lim);  // 获取 RW 缓冲区
  // ... 逐字节发射指令 ...
  emit_loadi(RID_RET, 42);   // 写入：48 c7 c0 2a 00 00 00
  emit_jcc(CC_NE, exit_label); // 写入：75 XX（相对偏移）
  // ...
  lj_mcode_commit(J, mctop);  // 提交已写字节
}
```

发射器（`lj_asm.c` + `lj_asm_x86.h`）向缓冲区直接写入原始 x86-64 机器码字节。每条 IR 指令变成一或多个字节。标签解析为相对偏移。输出是连续的原生机器码块。

**第 3 步——切换为可执行：**
```c
// 汇编完成后
mprotect(buf, sz, PROT_READ | PROT_EXEC);
// 页现在是 RX——可以执行，但不可写
```

`mprotect` 把页面权限从 RW 翻转为 RX。内存现在是可执行的机器码。任何写入尝试都会段错误——这是安全保证。

**第 4 步——作为函数指针调用：**
```c
// 追踪入口点是 MCode 缓冲区中的函数指针
typedef void (*TraceFn)(jit_State *J, GCtrace *T);
TraceFn f = (TraceFn)T->mcode;  // T->mcode 指向机器码起始位置
f(J, T);  // 执行编译后的追踪！
```

CPU 从缓冲区取指令并原生执行。追踪一直运行到退出（通过守卫失败或返回），此时退出处理器接管。

### W^X 安全规范

写异或执行规范对安全至关重要。默认情况下（`LUAJIT_SECURITY_MCODE`）：

- **生成期**：页面是 RW（读-写，不可执行）
- **执行期**：页面是 RX（读-执行，不可写）
- `mprotect()` 只在权限实际变化时才切换

这防止了代码注入攻击：攻击者无法向可执行内存写入 shellcode，因为可执行内存永远不可写。

### 对比：DynASM vs JIT 发射器

| 方面 | DynASM（构建时） | JIT 发射器（运行时） |
|------|-----------------|-------------------|
| 何时运行 | 构建时 | 运行时 |
| 内存分配 | 静态（在二进制中） | `mmap()` 运行时 |
| 输出 | .text 段的 C 数组 | `mmap` 缓冲区 |
| 执行 | 直接调用（代码在二进制中） | `mprotect()` + 函数指针 |
| 安全 | 不适用（静态代码） | 需要 W^X 规范 |
| 架构 | 一份源码生成 7 个目标 | 每个构建一个目标 |

两者遵循相同模式：**分配 → 写机器码 → 设为可执行 → 调用**。DynASM 在构建时做（输出为编译进二进制的 C 数组）；JIT 发射器在运行时做（写入 `mmap` 的内存）。

## 追踪式 JIT 何时胜出（何时失利）

追踪式 JIT 并非普遍更好——它对特定工作负载更好。理解它何时胜出、何时失利，告诉你何时该选追踪式 JIT（或何时该避开）。

### 追踪式 JIT 胜出的场景

**类型稳定的紧密循环**。经典场景：循环中的数值计算。追踪录制一次类型，守卫在每次迭代验证，编译后的代码运行时没有任何类型分派开销。LuaJIT 在数值循环上达到接近 C 的性能。

**快速预热**。因为只编译热路径，JIT 几乎立即开始产出优化代码。方法 JIT 经常需要编译完整函数才能看到加速；追踪式 JIT 在 56 次迭代后就编译第一个热循环。

**路径特化优化**。追踪为精确观察到的类型、分支方向、调用目标特化。总是处理整数的循环得到整数特化代码。总是调用同一函数的循环得到内联调用。

**自然内联**。追踪自然跨越函数边界。如果函数 A 在热循环中调用函数 B，追踪录制对 B 的调用，把 B 的函数体内联进来。不需要单独的内联过程。

### 追踪式 JIT 失利的场景

**复杂控制流**。如果循环有很多分支（switch 语句、深层嵌套 if-else），每个分支点都能产生侧追踪。追踪爆炸消耗内存和编译时间。方法 JIT 处理复杂 CFG 更从容。

**不稳定类型**。如果变量的类型在迭代间变化（数字，然后字符串，然后表），追踪在每次类型变化时去优化。反复去优化的开销超过编译收益。

**冷代码偶尔有热路径**。带分层的方法 JIT 处理这种情况很好：冷代码在解释器运行，热代码逐步获得更多优化。追踪式 JIT 只编译热路径，所以冷但重要的代码可能永远得不到优化。

### 真实性能

LuaJIT 在游戏脚本（紧密循环、类型稳定、数值计算）和嵌入式系统（快速预热、低内存）中占主导地位。在复杂 Web 应用（不稳定类型、复杂控制流、大代码库）上输给 V8——V8 的分层方法 JIT 加 TurboFan 能应用全函数优化。

现代趋势是**混合**：V8 的 TurboFan 使用分析数据（像追踪式 JIT）来指导方法编译。PyPy 的元追踪 JIT 追踪解释器本身。追踪式 JIT 和方法 JIT 的界限正在模糊。

## 精准打击实战——一个完整示例

让我们追踪一个完整的例子：对数组求和。

### Lua 源码

```lua
local function sum_array(arr)
  local sum = 0
  for i = 1, #arr do
    sum = sum + arr[i]
  end
  return sum
end

-- 用数字数组调用
local result = sum_array({1, 2, 3, 4, 5})
```

### 第 1 步：解释器运行，热计数器递减

`sum_array` 的第一次调用在解释器中运行。`FORL` 循环头在每次迭代递减热计数器。经过 56 次调用（或单次调用长数组的 56 次迭代），计数器归零。

### 第 2 步：录制开始

`lj_trace_hot()` 触发。录制器（`lj_record_ins()`）开始将字节码翻译为 IR。它记录实际走过的路径：循环体以 `arr` 为表、`i` 为整数、`sum` 为数字执行。

### 第 3 步：追踪录制

录制的 IR（简化）：

```
 ─┬─────────────────────────────────────────────────────────────────────
 │  [1] FLOAD arr, ┬──┬        ; 从槽 0 加载 arr
 │  [2] FLOAD #arr, ┼──┼──┬     ; 加载数组长度（从 #arr 展开）
 │  [3] ISNUM i, ┬──┼──┼──┬     ; 守卫：i 是数字
 │  [4] ISNUM sum, ┼──┼──┼──┼──┬  ; 守卫：sum 是数字
 │  [5] TGETR arr, i, ┼──┼──┼──┼──┬ ; 整数键表获取
 │  [6] ISNUM [5], ┼──┼──┼──┼──┼──┬ ; 守卫：arr[i] 是数字
 │  [7] ADD sum, [5], ┼──┼──┼──┼──┼──┼ ; sum + arr[i]
 │  [8] ADD i, 1, ┬──┼──┼──┼──┼──┼──┼ ; i + 1
 │  [9] LE i, [2], ┼──┼──┼──┼──┼──┼──┼──┬ ; i <= #arr?
 │  [10] JMP ->loop_start          ; 条件成立则循环回跳
 ─┴─────────────────────────────────────────────────────────────────────
```

[3]、[4]、[6] 处的守卫验证类型假设。任一失败则追踪退出。

### 第 4 步：优化

录制后优化运行：
- **窄化**：`sum` 和 `arr[i]` 已知为整数 → 使用 int32 运算
- **循环优化**：循环体通过复制替换展开
- **死代码消除**：删除无用计算

### 第 5 步：汇编

发射器向 `mmap` 的 RW 缓冲区发射 x86-64 机器码：

```asm
; 序言——从 VM 加载状态
mov r12, [rbx]        ; BASE = vm->base
mov r14, [rbx+8]      ; 调度位置

; 循环开始
->loop_start:
mov eax, [r12+8]      ; 加载 i
mov ecx, [r12+16]     ; 加载 sum
; 守卫：i 是整数
test eax, 0x7ff00000
jnz .exit_guard_1
; 守卫：sum 是整数
test ecx, 0x7ff00000
jnz .exit_guard_2
; 表获取：arr[i]
mov rdx, [r12]        ; 加载 arr 指针
mov edx, [rdx+rax*4-4] ; arr[i]（0 索引，int32 数组）
; 守卫：arr[i] 是整数
test edx, 0x7ff00000
jnz .exit_guard_3
; 加
add ecx, edx          ; sum += arr[i]
; 递增
inc eax               ; i++
; 循环条件
cmp eax, [r12+24]     ; 比较 i 与 #arr
jle ->loop_start      ; 循环回跳

; 尾声——返回 sum
mov [r12+16], ecx     ; 存回 sum
ret
```

### 第 6 步：执行

缓冲区被 `mprotect` 为 RX 并调用：

```c
typedef void (*TraceFn)(jit_State*, GCtrace*);
TraceFn fn = (TraceFn)T->mcode;
fn(J, T);  // 以原生速度运行编译后的循环
```

对于数字数组，这比解释器快约 10 倍——没有类型分派、没有字节码解码、没有 PC 和 BASE 寄存器的内存加载。

### 第 7 步：去优化（类型变化时）

如果之后用 `{1, 2, "three", 4, 5}` 调用 `sum_array`：

1. 追踪对 `arr[1]=1` 和 `arr[2]=2` 正常运行
2. 到 `arr[3]="three"` 时，守卫 [6] 失败（是字符串，不是数字）
3. 退出桩保存寄存器状态并调用 `lj_vm_exit_handler`
4. `lj_snap_restore()` 重建解释器状态：`i=3`，`sum=3`，PC 在循环体
5. 解释器从该点恢复，处理字符串情况

追踪不会被丢弃——它对数字前缀仍然有效。如果字符串情况发生得足够频繁，可能会编译一条侧追踪。

## 常见问题解答

### 为什么 V8 不用追踪式 JIT？

V8 其实用过——Firefox 的 TraceMonkey 率先将追踪式 JIT 用于 JavaScript，V8 早期也实验过追踪。但方法 JIT 加分层在复杂 Web 应用上胜出了。原因是 Web 上的 JavaScript 代码高度多态（类型频繁变化）且控制流复杂（大量分支、闭包、属性访问）。方法 JIT 处理得更好，因为它们编译整个函数，可以跨分支优化。追踪式 JIT 在多态代码上遭遇追踪爆炸。现代 V8 使用混合方案：TurboFan 用分析数据（像追踪式）指导方法编译。

### 如果追踪反复去优化会怎样？

LuaJIT 把出错的字节码位置**加入黑名单**。在同一个守卫点超过阈值次数的去优化后，LuaJIT 停止尝试追踪该循环。代码永远在解释器中运行。这防止了病态情况——JIT 浪费时间去编译立即失败的追踪。

### 追踪能跨越函数边界吗？

能——这是追踪式 JIT 的超能力之一。当追踪录制一个函数调用时，它可以继续录制到被调用函数内部，实际上把它内联进来。生成的追踪跨越多个函数。这在录制时自然发生；不需要单独的内联过程。代价：如果被调用函数很大，追踪也会变得很大。

### 追踪占用多少内存？

每条追踪都很紧凑：IR（SSA 指令）、快照数组和机器码。典型追踪从几百字节到几 KB。但追踪树可以增长：一个有 N 个分支点的循环在最坏情况下能产生 2^N 条追踪。实践中，黑名单和追踪限制使内存有界。LuaJIT 默认最多 2MB MCode 区域。

### LuaJIT 的 JIT 还是最快的 Lua 实现吗？

是的，优势明显。LuaJIT 2.1 在数值和表密集型工作负载上一致优于其他 Lua 实现（标准 Lua 5.4、LuaJIT 分支、mlua 等）。追踪式 JIT 结合了类型特化、路径特化和低开销，对于 Lua 典型使用场景很难被超越。
